# GI1 research: filing GitHub issues from the kit (2026-10-25)

What `cc-smart-dev-kit issue file` (D67) rests on, read from the current docs and the installed
`gh` (2.102.0) on 2026-10-25, not from memory. The design that follows is in
`docs/design/issues.md`.

## 1. Finding the double: list by label, compare the marker ourselves

**Question.** The kit hides a fingerprint in an HTML comment in the issue body. Can GitHub's
search find an issue by that text?

- GitHub's search page for issues and pull requests says `in:body` searches "the title, body,
  comments" and never mentions HTML comments or hidden text — it does not say a comment is
  indexed, and it does not say it is not.
  <https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests>
- Search is also eventually consistent (a new issue is searchable after a delay), and has its own,
  stricter rate limit than the REST API
  (<https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api>: search
  endpoints "have more restrictive limits"; no number is given there).

**Decision.** Do not depend on search. Every issue the kit files carries the `found` label
(`workflow.issues.foundLabel`). `issue file` lists that label's issues once, in every state,
with `gh issue list --repo … --label <found> --state all --limit 1000 --json number,url,body`
(the flags are in `gh issue list --help`, 2.102.0), and looks for the marker line in the bodies
itself. `gh` pages the list by itself up to `--limit`; a list that returns the limit is refused,
because the double might lie beyond it. One list = a few REST/GraphQL requests, far inside the
5,000 requests per hour of an authenticated user.

A side effect that is also a defence: only an issue that carries the label can be taken for ours,
so a marker pasted into someone else's issue does not make the kit rewrite it.

## 2. Writing: `gh issue create`, `gh issue edit`, `gh label create`

- `gh issue create` has `--repo`, `--title`, `--body-file` (`-` reads standard input), `--label`
  (repeatable). It prints the new issue's URL on stdout.
  <https://cli.github.com/manual/gh_issue_create>
- `gh issue edit` has `--body-file` (`-` = standard input) and changes the title only when
  `--title` is given, so an update that passes only `--body-file` leaves title and labels alone.
  <https://cli.github.com/manual/gh_issue_edit>
- A label that does not exist makes `gh issue create --label` fail, so the kit lists the labels
  (`gh label list --json name --limit 1000`) and creates a missing one (`gh label create`).
- The body goes on standard input (`input` on the runner), never in an argument: no length limit
  of the command line, nothing in a process list.

**Rate limits for a write.** The primary limit is 5,000 requests per hour; the secondary limit
for content creation is "no more than 80 content-generating requests per minute" and "no more
than 500 per hour" (the rate-limit page above). One finding is at most one create (plus the label
creates the first time); a loop that files hundreds of findings in a minute would meet the
secondary limit and `gh` would report it as a failure, which `issue file` reports as a refusal.

## 3. Who may do what (the doctor line)

GitHub's repository roles
(<https://docs.github.com/en/organizations/managing-user-access-to-your-organizations-repositories/managing-repository-roles/repository-roles-for-an-organization>):

| Action | Read | Triage | Write |
|---|---|---|---|
| Open issues | yes | yes | yes |
| Apply and dismiss labels | no | yes | yes |
| Create, edit, delete labels | no | no | yes |

So: **Read** cannot apply the `found` label — a failure. **Triage** applies labels but cannot
create one — a warning (it works while the labels exist). Write, Maintain and Admin are fine.
`gh repo view --json viewerPermission` names the role; `visibility` and `hasIssuesEnabled` come
in the same call, so `issue file` and `doctor` read all three at once.

## 4. A public repository

- A public repository's issues, and every edit of them, are readable by everyone. The kit says
  `public` in its answer line, and a public `origin` needs its own switch,
  `workflow.issues.allowPublic` (the owner's yes, 2026-10-25), on top of `issues.enabled`.
- `gh repo view --json visibility` prints `PUBLIC`, `PRIVATE` or `INTERNAL`. Only `PUBLIC` is
  public; an internal repository is visible to the enterprise only.

## 5. Which repository

- `gh issue …` takes `--repo [HOST/]OWNER/REPO`. The kit passes `github.com/<owner>/<name>`
  from `git remote get-url origin` on every call, so neither `GH_REPO`, the folder's own
  guess, nor a fork's upstream decides it (`gh repo set-default` is not used).
- Only github.com: a GitHub Enterprise host cannot be told from another git host by its URL, so
  an `origin` elsewhere is refused. (A later release may take a configured host.)
- `gh auth status --hostname github.com` exits 1 when the account has authentication issues
  (`gh auth status --help`) — the doctor's "logged in" test.

## 6. Text that must not leave

No existing helper detects secrets: `redactUrlsIn` (`src/setup/marketplace-access.ts`) hides
credentials in a URL for printing, and `maskSecrets` (`src/gateway/plain-text.ts`) masks a log
line loosely (any 32-character run), which would refuse every commit hash — and the router
bundle imports it, so changing it restarts every router. The new screen (`src/issues/screen.ts`)
is the one home of *detecting*, with a line and column; it shares the URL scheme list
(`TOKEN_SCHEMES`) with `redactUrl`.

## What is not proved

- Whether GitHub's search indexes an HTML comment. Not needed: the design avoids search.
- That two `issue file` calls at one moment with one fingerprint cannot make two issues: they can
  (list, then create), and no lock spans GitHub. Documented as a limit.
- GitHub Enterprise Server hosts. Refused by design.
