Date: 2026-10-25

`docs/claude-code-contract.md` § The gateway; the code that relies on a changed fact is listed
below, for the lead to send to a fix phase. No code was changed here.

**Why.** GP2 (a project's gateway state), GP3 (`launch`), GP4 (doctor, restore, the Gateway
card) and GP5 (an explicit URL instead of a removed key) rest on R6's live proofs
(`.claude/research/2026-10-23-r6-proofs.md`, GP0). GP0's session was answered mostly by an
affordable model, and it committed no probe scripts, so nobody could tell which results it
really saw. This phase built its own probes from the proofs' questions, ran them, and only then
compared with GP0's results.

**Version.** Claude Code **2.1.310** (`claude --version`), on Linux. GP0 ran 2.1.309.

## How the probes ran

- **Our own scripts**, committed in `.claude/research/r6-recheck/`: `lib.ts` (the fake
  Anthropic, the throwaway world, the clean run, the stream-json driver, the tmux harness) and one
  script per proof. Run one from the repo root:
  `R6_TMP=<a temp folder outside any git repo> bun .claude/research/r6-recheck/<script>.ts`. Each
  prints its result and leaves `result.json` and `log.jsonl` in its world folder.
- **A fake Anthropic per source**: a Bun server on a free port (port 0; `lib.ts` refuses the live
  router's 20100), answering `HEAD /api/hello`, `POST /v1/messages` (a stream or JSON, the text
  `ok (<label>)`) and `count_tokens`, and logging every request's path, headers (a credential's
  value only as `<present>`), body size, model and where a marker string appears. Its answer names
  its label, so stdout says which fake answered too.
- **A throwaway `HOME` and `CLAUDE_CONFIG_DIR`** for every run but P1 — so, unlike GP0, not even
  the person's global `CLAUDE.md` was read. **A clean environment**: only `PATH`, `HOME`,
  `CLAUDE_CONFIG_DIR`, the fake key, `LANG`, `DISABLE_AUTOUPDATER` and the case's shell URL; the
  calling session's own variables (its `ANTHROPIC_BASE_URL` among them) never reached a probe.
- **Every project folder is a new git repo** (case 17 of P6 excepted, by design), and no repo
  sits above the temp area.
- `claude -p --model haiku --strict-mcp-config --no-session-persistence -- 'Say ok'`; P5 and P7
  hold one `claude -p --input-format stream-json --output-format stream-json` open across turns.
- **Interactive probes** (P8's second half, P9, P13's Escape) run in a private tmux server (its own
  socket, no `tmux.conf`). **A harness trap, found and fixed:** at first P9's second session
  sometimes died at its start (exit 1). Its debug log said "workspace trust not accepted": the
  first session's claude, still exiting after `kill-server`, saved `.claude.json` from memory
  and dropped the trust record the probe had just written for the next folder; the next session
  opened on the trust dialog, and the probe's Enter picked its default, "No, exit". `Tmux.kill`
  now waits until the session's process is gone; P9 then passed three runs in a row. (The kit
  writes no trust record, so this is no contract row; it is why a probe must never edit
  `.claude.json` while a session of the same config may still be exiting.)
- **P1** used the person's own config folder and login, for one `claude -p --model haiku`, with a
  `--settings` file holding only the URL and `disableAllHooks` (so the config's own hooks did not
  run beside it), the session not saved, and only the init and result fields printed.
- **Background traffic** still left the machine (Claude Code's own fetches that do not use the
  base URL: the debug log showed a bootstrap call answered 401 with the fake key). The model
  traffic did not: "against a fake Anthropic", not "offline".

## What changed, and the code that relies on it

Three facts differ from GP0's. No code was changed here; each item is for a fix phase.

### P6 — the starting folder's own `settings.local.json` is read too

**The fact (2.1.310).** For an `env` key, Claude Code reads `settings.local.json` from **both**
the main checkout's root and the folder the session starts in. Key by key, the main root's
wins — a main-root file whose `env` holds another key but not the URL leaves the URL to the
starting folder's own file (cases 18, 19) — and the starting folder's own local file comes
next, before the starting folder's `.claude/settings.json` and the user file. Outside git, the
folder's own local file is read. Proved for `ANTHROPIC_BASE_URL`; another `env` key such as
`ANTHROPIC_API_KEY` very likely follows the same rule (not run); `apiKeyHelper`, which is not
an `env` key, is not known.

**What relies on the old fact, and what breaks:**

- `src/gateway/project-state.ts` › `stateFrom` (lines 378-401) builds `files` as
  `personalFileOf(checkout)` (the main root's local file), `teamFileOf(asked)`, then the
  machine's file — and reads no personal file at all when `checkout === null`. Its header's P6
  bullet says the same. The starting folder's own local file must join `files`, not only the
  URL decision, because several readers walk `files`:
  - the URL decision (`choice`, `effective`): `gateway project status`, `gateway projects`,
    doctor's project lines and the portal's Gateway card report the team or machine state while
    the session uses that folder's own value;
  - the login-override refusal (`src/gateway/commands-project.ts:227-245`, built from
    `view.files`): a worktree's own local file holding `ANTHROPIC_API_KEY`,
    `ANTHROPIC_AUTH_TOKEN` (or, not proved, an `apiKeyHelper`) does not stop `gateway project
    on`, and that worktree's sessions then send the key, not the login, through the router;
  - doctor's model-key and subagent warnings (`src/gateway/doctor.ts:438`, `:454`) miss what
    that file sets.

  **The sure trigger** is `gateway project status` run in a subfolder, a linked worktree or a
  folder outside git (the folder or `--folder`). `gateway projects`, doctor's lines, the portal
  card and `gateway off`'s list (`src/gateway/commands.ts:2652`) ask about each listed project's
  root; they meet the case only if a listed root can be a linked worktree or a folder outside
  git — not checked here.
- `src/gateway/commands-project.ts`: the header's P6 paragraph (lines 10-13) and
  `savedStateLines`: "Every session of this project — the main checkout, its subfolders and its
  worktrees — reads it." Still true, and the main root's file wins; but after `gateway project
  default` a worktree or subfolder with its own local file uses that file, and the lines do not
  say so. `portal/src/lib/gateway.ts:105` (`personalFileWords`, "Every worktree of the project
  reads it.") is the portal's copy of that sentence.
- `src/cli/restore.ts` and `src/setup/restore.ts` (GP4a: `restore` counts a project's own key):
  they track the files the kit wrote — the main root's local file — never a copy in a worktree.
  A worktree gets a copy when a project's `.worktreeinclude` names `.claude/settings.local.json`
  (`src/worktrees/include.ts` copies only git-ignored files, and the kit's exclude line makes the
  personal file one; Claude Code does the same for its own worktrees).
  **Breaks, when such a copy holds the router's address:** `restore` stage 1 writes Anthropic's
  address into the main root's file, which wins, so the worktree's sessions go to Anthropic;
  stage 2 stops the router and then removes that key — and a running session in the worktree
  moves to its copy's router address (P7's worktree cases show the move, live), as does every
  new session there. Each then fails until the person removes the copy. `gateway project
  default` does the same with the router still running: the worktree keeps the old route. No
  doctor line names the copy.
- Tests that pin the old fact: `src/gateway/project-state.test.ts` (its header, lines 6-8; the
  comment at line 167, "The subfolder's own local file is ignored by Claude Code"; and lines
  249-258, which pin `["team", "machine"]` for a folder outside git).
- Docs that state the old fact: `docs/gateway.md` § Per project ("Which file wins (P3)"),
  `README.md` (the `gateway project` paragraph), `plugin/skills/gateway/SKILL.md` (the personal
  file's paragraph).
- Not checked: whether other settings keys follow the same rule. `src/crew/bypass.ts` reads
  `permissions.defaultMode` from the checkout root's local file; these proofs cover `env` only.
- Outside this change (the reviewer's note): `commands-project.ts:232-233` already says a
  worktree's own committed team file is not part of the login-override check.

### P7 — a removed key falls through to the next file that sets it

**The fact (2.1.310).** A changed value reaches a running session within about a second (0.5 s
too early, 1.05 s enough). When a key is removed from a settings file — the whole file, the
`env` object, or only the URL with another `env` key kept — a running session takes the value
the rest of the chain still sets (another settings file, the starting folder's own local file
included), by the next turn 3 s later. Only when **no** settings file sets the key any more
does the session keep its last value until it restarts; the shell's own export does not come
back (a new session in that folder takes it).

**What relies on the old fact, and what breaks:**

- `src/gateway/commands-project.ts`: the header's P7 paragraph (lines 24-25), `savedStateLines`'s
  line for `default` — "A session already running keeps the value it had until it restarts: a
  removed key never reaches a running session." — and `PROJECT_HELP` (lines 660-666, "a removed
  one waits for a restart"). **Wrong in the common case**: `gateway on` writes the machine's
  settings file, so after `gateway project default` a running session moves to the machine's
  value within seconds. **Breaks:** the person is told to restart for nothing; nothing else.
  The test `src/gateway/commands-project.test.ts:391-404` pins the `savedStateLines` sentence.
- `portal/src/lib/gateway.ts:95-98`: `runningWords("default")`, the portal's Apply text —
  "Default removes the address, and a running session never sees a removal: restart a session
  already running in this project." Same break, in the portal; pinned by
  `portal/src/lib/gateway.test.ts:157-166`.
- `src/cli/restore.ts` › `fileUsesRouter`: a file whose address key is gone but another owned key
  stays answers "still routes to the router" ("a removed key never reaches them, P7"). It is
  true only when no other file sets the key. **Breaks:** nothing unsafe — it can only keep the
  router running longer than needed.
- `src/setup/restore.ts` (`writeInstead`'s comment) and `src/gateway/settings.ts` (the comments
  at lines 6-11, 82-83 and 360-363): the reason they give is incomplete. **The design stays
  right**: a written address reaches every running session for which that file decides,
  whatever the files below it in the chain hold; a removal reaches them only when a file below
  sets the key. (A project's own local file holding the router still beats a write to the user
  file; `gateway off` names such projects for that reason.)
- Text that states the old fact: `docs/gateway.md` § Per project ("Running sessions (P7)") and
  its two later mentions, `docs/design/gateway.md` (the running-session bullet),
  `docs/design/portal.md:629-630` (Apply's words), `docs/roadmap.md:326-329` ("Answered
  (2026-10-23)"), `README.md` (lines 320, 788, 803 and 1176: `restore`, the command table, the
  `gateway project` paragraph, the portal's project page), `plugin/skills/gateway/SKILL.md`,
  `.claude/rules/setup-and-managed-files.md` § `--dry-run` and `restore`, and comments in
  `src/portal/server.test.ts:1854`, `src/cli/gateway-cli.test.ts:1480` and
  `src/gateway/commands.test.ts:330`.

### P13 — `claude -p` exits 0 on SIGINT

**The fact (2.1.310).** SIGINT to `claude -p` while its request is held: exit 0, stdout
`Execution error`. This machine's `timeout` (uutils coreutils 0.10.0) exits 130 itself when it
gets the SIGINT; GNU `timeout`, which documents passing on the command's own status, was not
tried.

**What relies on it:** nothing found. The kit's own 130s are its own commands' Ctrl+C codes
(`src/cli/ui/prompt.ts`, `src/entries/portal.ts`, `src/browser/token.ts`, `src/cli/claude-mem.ts`,
`src/gateway/commands.ts`); none reads a `claude -p` exit code. Only the contract row changes.

### A detail, not a change: the startup `HEAD` and a profile path

With the URL (and its `/p/<profile>` path) in a project's file, the startup `HEAD /api/hello`
goes to the user file's or the shell's URL, without the path; only the message requests carry
the profile. The router strips `/p/<name>` from a `HEAD` too (`src/gateway/router.ts`), so
nothing breaks — but a `HEAD` says nothing about which profile a session uses.

## For the lead: P8's `--bg` half and P10

A crew session may not start `claude --bg`, so these two are the lead's. Each script refuses to
run inside a crew session (`CC_SMART_DEV_KIT_CREW` set) unless given `--dry-run`, which sets the
world up and prints the exact `claude --bg` lines; both dry runs were run here. Each real run
stops and removes the sessions it started and ends every process left with its throwaway config
(`leftoversEnded` lists them).

```sh
R6_TMP=<a temp folder outside any git repo> bun .claude/research/r6-recheck/p8-bg-trust.ts
R6_TMP=<a temp folder outside any git repo> bun .claude/research/r6-recheck/p10-bg-settings.ts
```

- **P8 (`--bg`), `untrusted`:** proved if `exitCode` is 1, `stderr` says ``Workspace not trusted.
  Run `claude` in <folder> once and accept the trust prompt, then retry.``, and `requests` is
  empty; refuted if a session starts. **`trusted`:** `backgrounded · <id>`, and `messagesTo` is
  `L` — the project's local file reaches a `--bg` session once trusted. `D` there refutes it.
- **P10, case 1** (`--settings` with the URL and an `apiKeyHelper`, no key in the caller's
  environment): proved if `helloTo` and every `messagesTo` entry is `C`, none `D`, and
  `end.logs` shows `ok (C)`. **Cases 2 and 3** (the key in the caller's environment; the key in
  the file's `env`): GP0's credential finding holds if `end.logs` shows "Not logged in" and
  `messagesTo` is empty; a message request at `C` refutes it. **Case 4** (untrusted): exit 1,
  `Workspace not trusted`.
