## 1. Claude Code facts

### 1.1 What Claude Code retries by itself (no watchdog)
- **Which errors it retries:**
  - 408, 409, 5xx (529 included), dropped connections, and timeouts before any output.
  - A **429 without quota headers**. A 429 counts as a quota limit when it carries `anthropic-ratelimit-unified-representative-claim` or `-overage-status`. On a claude.ai subscription, a 429 with those headers is never retried.
  - The `x-should-retry` header is honoured: `false` means no retry; `true` means retry (on a subscription, only for a non-quota 429).
  - Sources: [checked: code.claude.com/docs/en/errors § Automatic retries; binary: should-retry function near offset 249466000 (`Cmn`/`J5n`, offset 242222196)].
- **How many times:** 10 by default (11 requests), set by `CLAUDE_CODE_MAX_RETRIES` up to a cap of 15. [checked: errors § Tune retry behavior; env-vars; binary constants `_fr=10`, `vQe=15`]
- **Backoff:** 500 ms doubling, capped at 32 s, plus up to 25 % jitter. [checked: binary `xN` at 240347909, `fe=500`, `YGo=0.25`] This matches our own live row: 11 requests in 172 s. [checked: `docs/claude-code-contract.md:140`]
- **`retry-after` is honoured as a minimum:** the wait is `max(retry-after, backoff)`. [checked: binary `xN`; changelog 2.1.98, `~/.claude/cache/changelog.md:6452`]
- **A wait above 60 s fails the request at once** (`api_request_retry_after_too_long`, constant `Afr=60000`). So a `retry-after` of 61 or more ends the turn on the first answer. [checked: binary near 249462xxx; changelog 2.1.94, line 6558]
- **Our router passes a backend's `retry-after` through with no cap** (`responseHeaders`, `src/gateway/router.ts:353-366`). [checked]
- **A 529 for Claude Code's own background calls is dropped with no retry** when no watchdog is set. [checked: binary `api_request_overload_background_dropped`] Which calls count as background (titles, summaries) is [hunch].
- **With a `fallbackModel` set:**
  - a 5xx other than 529 switches model on the **first** error;
  - a 529 switches model after 3 in a row;
  - a 429 never switches model.
  - [checked: binary `IQe`, `NZ=3`; settings-reference § fallbackModel] Today the router answers 502 for "no target answered" (`router.ts:1810`). So a person with a fallback model is moved off the slot at once.

### 1.2 A usage-limit 429, a rate-limit 429, and a 429 from a gateway
- **Usage limit** (quota headers present, `unified-status: rejected`):
  - It is sent once and not retried. The turn ends with "You've hit your session limit · resets …".
  - A subagent ends too. An interactive session may auto-continue (§ 1.4).
  - [checked: errors § Usage limits; contract row `docs/claude-code-contract.md:139`]
- **Short throttle** (no quota headers): retried under the 1.1 rules, then "API Error: Server is temporarily limiting requests (not your usage limit) · <message>". [checked: errors § Server is temporarily limiting requests; contract row 140]
  - That is exactly what our router sends when a backend chain is used up: today's second failure. [checked: router log, see 1.8]
- **Through a custom `ANTHROPIC_BASE_URL`:**
  - The same rules apply, read from the headers. The message names the gateway host. An HTML 429 page is shown by its title.
  - A gateway's spend-limit 429 with `x-should-retry: false` is not retried. [checked: errors § Request rejected (429), § Spend limit reached]

### 1.3 The retry watchdog ("unattended retry mode")
- **What it does with `CLAUDE_CODE_RETRY_WATCHDOG=1`:**
  - 429 and 529 are retried with no limit on the count, up to 5 min apart (`wmn=300000`).
  - When the answer carries `anthropic-ratelimit-unified-reset`, it waits until that reset. One wait is capped at 6 h (`TQe=21600000`). [checked: env-vars row; binary constants]
  - It shows a "Retrying in …" status every 30 s (`M_o=30000`). [checked: binary]
  - Other transient errors (5xx, timeouts, dropped connections) get 300 retries, about 3 h. [checked: env-vars; changelog 2.1.199, line 4643]
  - It fails at once on a spend-limit or out-of-credits 429. [checked: changelog 2.1.239, line 3624]
- **`…_MAX_WAIT_MS`** caps the total wait on 429/529 for each request. Unset means no limit. Added in 2.1.295. [checked: env-vars; changelog line 633]
- **`…_MAX_USAGE_LIMIT_WAIT_MS`** (2.1.301): a usage limit whose reset is further away than this fails at once, unless paid extra usage is allowed. [checked: changelog line 200; binary `api_request_usage_limit_wait_too_long`] It is **not on the env-vars page**: it exists only in the changelog and the binary.
- **`…_USAGE_LIMIT_RECHECK_MS`** (2.1.305, accepts 60000 to 10800000):
  - It is the shortest gap between checks of whether a limit was lifted early.
  - Checks run only for a claude.ai session or weekly limit, with no usage credits in use, and not under `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. [checked: env-vars]
  - The gap grows exponentially, up to 3 h. [checked: binary]
- **Which sessions:** it is a process environment variable, and the code checks no attended or unattended flag. So it applies to every request of the process: the main session, in-process subagents, `-p`, and `--bg` sessions (through the settings `env`, per agent-view § settings/env). [checked: binary `h5()`]
  - Interactive use is not documented. The docs say it is "for unattended sessions". [hunch: works interactively, proof P-BR7]
  - Whether it is honoured from a settings `env` block is [hunch: proof P-BR1d].
- **A waiting request can be woken:** each subagent's retry has a `subscribeRetryWake` hook. Changelog 2.1.198 says "messaging a stuck teammate wakes it to retry immediately". [checked: binary near 273475632] Whether a SendMessage to a waiting subagent wakes it is [hunch: proof P-BR5].
- **Risk: the subagent stall timer** (`CLAUDE_ASYNC_AGENT_STALL_TIMEOUT_MS`, default stream-idle plus 300 s, about 10 min) may cut a background subagent during a long wait. [checked that the timer exists: binary near 255052xxx] Whether retry waits reset it is [hunch: proof P-BR3]. Changelog 2.1.260 treats long watchdog waits in agents as a normal case.

### 1.4 `autoContinueAtUsageLimit` ("Continue automatically at usage limit")
- It is read from user or managed settings and is on by default. [checked: settings-reference index; interactive-mode § Wait for a usage limit to reset]
- **Where it applies:** interactive sessions on a claude.ai subscription, with a saved claude.ai login as the active credential (allowed behind a gateway).
- **Where it does not start by itself:**
  - Background sessions and `-p`: not offered at all.
  - Remote Control and teammate sessions: a person must start it.
  - A reset more than 24 h away.
  - An Opus or Sonnet limit while the session runs a model outside that family.
- **What it does at the reset:** it prompts Claude to pick up the task, without resending the last message. It re-arms at most twice in a row. [checked: interactive-mode]
  - The continuation prompt goes through `UserPromptSubmit`: a hook that blocks it ends the wait. [checked: same page]
  - Notification types `quota_auto_resume_fired`, `_stale` and `_disabled` exist, since 2.1.234. [checked: hooks § Notification]
- **What ends the wait:** a `/login` account switch, exiting, a prompt you send, `/clear`. [checked]
- **Subagents:** not covered. They end on the error, and recovery is "ask Claude to retry the task or resume the subagent". [checked: sub-agents § API errors in subagents]
- **This setting only reacts to Anthropic's quota 429.** Our router's 429 has no quota headers, so it never triggers it. [checked by the 1.1 rule]

### 1.5 How long one request may stay open
- **`API_TIMEOUT_MS`** defaults to 600000 ms (10 min): the time an attempt has to get its response headers. It does not limit a stream after the headers. A non-streaming attempt is capped at 300 s in a local session. [checked: env-vars; errors § Request timed out]
- **Behind a custom `ANTHROPIC_BASE_URL`:**
  - **No first-byte deadline runs.** [checked: network-config § Streaming idle watchdogs]
  - A request that never gets headers "ends after 5 to 6 minutes". [checked: same section]
  - The byte watchdog is 300 s, and SSE keep-alive pings count as bytes. The event watchdog is 300 s: bytes reset it only "for up to about five minutes without a parsed event". [checked]
- **So the router may hold a request without sending headers for at most about 4 min (240 s) and stay safe.** [hunch: proof P-BR1c]
- Holding a stream open with pings buys nothing beyond about 5 min, and it commits a 200. [checked: same docs]

### 1.6 What a subagent's parent sees; resume
- **Foreground subagent:**
  - partial text gives partial output plus a cut-off note;
  - no output, or tool calls only, gives `Agent terminated early due to an API error: <detail>`.
- **Background subagent:** marked failed. The notification names the error and carries its last output. [checked: sub-agents § API errors in subagents; errors § Agent terminated early]
- **Resume:** `SendMessage` to the agent's id or name resumes it in the background with its full history. Explore and Plan agents return no id, so they cannot be resumed. [checked: sub-agents § Resume subagents; changelog 2.1.77, line 7025] Proved live today.
- **Background session:**
  - `claude --resume <id> --bg "<prompt>"` continues it in place (2.1.257 or later).
  - `claude respawn <id>` restarts it from its saved conversation.
  - A reply or attach wakes a stopped one.
  - [checked: agent-view § Manage sessions; P15 in the plan]
- **StopFailure:**
  - `error` is one of `rate_limit | overloaded | server_error | …`.
  - Optional `error_details`; `last_assistant_message` is the error text.
  - Its output is ignored.
  - It runs "instead of Stop", which means the main agent's turn. Whether it fires for a subagent's error is [hunch: no; proof P-BR2].
  - It runs in `--bg` sessions: our hook already stays quiet there on purpose (`src/hooks/stop-failure.ts:430`). [checked]
- **SubagentStop, PostToolUse and PostToolUseFailure on a subagent's API error** are not documented. [hunch: proof P-BR2]

## 2. Design

**Summary.** Three layers.
- **Router:** never answer "dead" for a backend capacity failure; hold briefly, then answer a 429 Claude Code retries.
- **Claude Code:** the watchdog is on for workers, and an opt-in for the person's own sessions; it gives the long wait (up to 12 h).
- **Kit:** pauses and resumes whatever still ends.

No layer changes prompt text, adds a target, or touches Anthropic's own answers.

### 2.1 Router layer: options

| Option | What it gives | Problems |
|---|---|---|
| A. Hold only | Picks up a chain change within 1 s | Claude Code cuts a request with no headers after about 5 min, and a non-streaming one after 300 s; alone it cannot bridge even an hour |
| B. Retryable status only (429 or 529 plus `retry-after`) | No open connections; with the watchdog, waits with no limit | Without the watchdog, about 10 min at most; a chain change is noticed only at the next retry (up to about 6 min with the watchdog's backoff) |
| **C. Both (recommended)** | A short hold with the config watched and one probe at a time, then a retryable 429 | More code; needs `deps.sleep` and a fake clock in tests |

**Without the watchdog, the bridge under C** is about 11 × (240 s hold + 60 s) ≈ 55 min. Today it is 10 retries over about 172 s, or an instant failure. [hunch: P-BR1]

**Exact behaviour (C)**, in `slotRequest` after `chain()`:
1. **When it applies.** Only when all of these hold:
   - the slot's breaker is on (`breakerOn`);
   - the path is `/v1/messages` (never `count_tokens`), not a safety check, and not an explicit `<backend>:<model>`;
   - every target in use failed with a **capacity kind** (the `FALLBACK_ANY` set at `targets.ts:430`: 408, 429, 5xx, 529, a network error, or a header or first-event timeout), or was skipped as resting;
   - the answer that would go back is **not Anthropic's own**. Anthropic's quota 429, 529 and 5xx always pass unchanged, so Claude Code's auto-continue, its watchdog reset wait and our StopFailure alert still see the real headers.
2. **No storm while open.** A resting last target is **not** asked. Only one request per target at a time may probe (a held request is the probe, so there is no synthetic traffic). The probe's success closes the breaker and releases the held requests through the normal chain. Its failure rests the target again (`cooldownSeconds`, up to 600 s).
3. **During the hold:**
   - Poll `deps.getConfig()` once per second per slot. It already stats the file and reloads on change (`config.ts:385-430`).
   - When the new chain's first target in use is not resting, run `chain()` at once.
   - The hold lasts at most `timeouts.breakerHoldMs`: default and ceiling 240 s for streaming, 60 s for non-streaming; `0` means no hold.
   - When the client hangs up, rest nothing, as today.
   - At most 64 held requests per slot. Above that, answer at once.
   - At SIGTERM, release every held request with retry-after 5, so the drain stays short.
4. **When the hold ends:** answer **429 `rate_limit_error`**:
   - `retry-after` = the seconds until the earliest rest ends, clamped to 1..60 (30 when unknown);
   - `x-should-retry: true`;
   - **never** any `anthropic-ratelimit-unified-*` header;
   - message: `cc-smart-dev-kit-router: every target of cc-smart-dev-kit-worker is limited or down since 21:05 (<target: reason, until>…); change it: cc-smart-dev-kit gateway slot worker <targets>`.
5. **Why 429 rather than 529:**
   - it is retried for every login type;
   - it never triggers a `fallbackModel` switch (a 529 does after 3);
   - a 529 for Claude Code's own background calls is dropped with no retry;
   - with the watchdog both count as capacity errors and are retried with no limit.
   - [checked: 1.1, 1.3] Claude Code shows "(not your usage limit) · <our message>".
6. **Bug fix even with the breaker off:** clamp every relayed backend `retry-after` to 60 or less in `responseHeaders`. Above 60, Claude Code fails at once.
7. **Heartbeat-only last target:** with the breaker on, hold the last target's stream until its first real event, for at most 180 s. A heartbeat-only stream then opens the breaker instead of stalling Claude Code for 5 min. Today's log shows many "no event in time (only heartbeats)" failures.

**The judge:** it never holds, and a `breaker` entry for `cc-smart-dev-kit-judge` is refused by the schema. Keep its 504 `timeout_error`. Auto mode already backs off on its own and stops after ten checks in a row with no answer [checked: changelog 2.1.280, line 2059]; a held check would freeze every action.

**Config, one home (`gateway.json`):**
- `breaker: {"<slot>": true|false}`, shaped like `fallback`. The default is on for every slot except the judge (`breakerOn` in `config.ts`). `gateway breaker <slot> on|off` writes it, mirroring `gateway fallback`.
- One global `timeouts.breakerHoldMs`. A per-slot hold would be a knob for a guessed future (`.claude/rules/dynamic.md` § The limit).

**Rules that stay** (`.claude/rules/gateway.md`): never change prompt text; never add a target; the login reaches only Anthropic; off means plain Claude, byte for byte.
- **One rule changes:** "A used-up chain returns its last answer, or a 502" (line 78) becomes: with the breaker on, a capacity-failed backend answer becomes the breaker's 429. Anthropic's own answer always passes.
- **Two rules are added:** never fake Anthropic's quota headers; the judge never holds.

**What the router logs and shows:**
- One `WARN cc-smart-dev-kit-worker: every target limited or down (…); holding requests up to 240 s, then asking Claude Code to retry (retry-after N)` when the breaker opens.
- The request line: `→ breaker(cc-smart-dev-kit-worker) 429 240013ms held probes=1`.
- One line when it closes: `… answers again after 1h12m; 37 requests held`.
- At most one reminder every 10 min while open.
- **State file:** `limit-state.ts` gains an optional `breakers: {"<slot>": {since, lastAt, targets:[{target,status,until}], held}}`. It is optional, so older readers ignore it. It is written once at open and cleared at close.
- The health page gets `breakers`.
- `gateway status` shows: `cc-smart-dev-kit-worker: all targets limited, holding requests since 21:05 (omniroute:a 429 until 21:07; …)`.
- The status line gets a part shaped like the existing warning part: `worker slot: every target limited since 21:05 → gateway slot worker <targets>`.

### 2.2 Claude Code layer: the watchdog for the 12 hours
- **Workers: on by default.** Put it in each worker's own `--settings` file (W1a's settings writer in `src/workers/start.ts`), with the values below. Workers are unattended sessions, which is what the watchdog is documented for.
  ```
  CLAUDE_CODE_RETRY_WATCHDOG=1
  CLAUDE_CODE_RETRY_WATCHDOG_MAX_WAIT_MS=<hours×3600000>
  CLAUDE_CODE_RETRY_WATCHDOG_MAX_USAGE_LIMIT_WAIT_MS=<same>
  CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS=300000
  ```
- **The person's own sessions: opt-in.** `setup` asks before anything runs, then writes the same four keys as owned keys under `env` in `~/.claude/settings.json` through `applyManagedJson`. A person's own value is kept (ForeignKeyError). `restore` removes them, and `doctor` gets a line.
  - This is the only way the lead's own subagents survive in-process.
  - **Trade-offs:**
    - every session on the machine waits (shown as "Retrying in …"; Esc cancels) instead of failing;
    - a person's `claude -p` script can hang for up to 12 h;
    - a broken setup spins up to 300 retries (about 3 h) on 5xx;
    - at a Claude limit the in-request wait replaces the auto-continue menu.
- **One home for "12 hours":** `workflow.limitWaitHours`, default 12, in `src/workflow/schema.ts`. It is read by the worker settings writer, `worker watch` and setup.
  - I prefer this over `workflow.workers.retryHours` because it also covers the person's own sessions.
  - Setup reads the person's own `workflow.json` only: the env keys are machine-wide.

### 2.3 Kit layer: whatever still ends
- **Workers (W2 `worker-role`):**
  - On StopFailure `rate_limit | overloaded | server_error`, set the state to `paused`, with `waitingFor` taken from the state file:
    - `{kind:"slot", slot, since}` when a fresh breaker record exists;
    - `{kind:"claude-limit", model, resetsAt}` when a fresh limit exists.
  - The store record gains an optional `waitingFor` (store schema versioning as K defined it).
- **`worker watch` (W1b) resumes a paused worker:**
  - **When:**
    - its slot's breaker record closed (another request got a 2xx);
    - the config changed so the slot's first target is no longer the resting or limited one;
    - a Claude limit's `resetsAt` passed (plus 1–2 min jitter) and the router dropped the limit;
    - or the person runs `cc-smart-dev-kit worker resume --paused` (the account-switch case).
  - **How:**
    - One worker first, as a canary. The others go 30 s apart, only after the router records a 2xx.
    - A worker that fails again within 15 min is re-paused with a doubled backoff (5 → 10 → 20 min).
    - It never resumes while the breaker is open or the limit is current, so there is no storm.
    - The transport is the same as `worker answer`: a message to a running worker, `claude --bg --resume <id> "<text>"` for a stopped one.
  - **The window:** after `limitWaitHours` from the first pause, mark the worker `failed` with the reason and tell the lead.
  - **Messages:** one line when the worker pauses and one when it resumes. Example: `W kit G1 guard paused: worker slot limited since 21:05; goes on by itself when it answers, until 09:05. Sooner: cc-smart-dev-kit gateway slot worker <targets> (gateway models lists them)`. For Claude: `… Opus at its session limit, resets 19:40. Sooner: /login with another account, then cc-smart-dev-kit worker resume --paused; or gateway slot opus <targets>`.
- **The lead's own subagents (W2 `lead-notes`):**
  - Record each failed subagent id in the lead record (`pausedAgents`). Sources: the Agent tool's result text (foreground, "Agent terminated early due to an API error"), and the background `<task-notification>` seen on `UserPromptSubmit`. Exactly which events fire is P-BR2.
  - The `worker-events` monitor prints "slot answers again: resume <ids> with SendMessage". That line wakes the lead (monitor wake proved in L1a.1).
  - On the auto-continue turn (it passes through `UserPromptSubmit`), the note lists which ids to SendMessage, never "start again".
- **The main session itself:** without the watchdog its turn ends. The breaker 429 is not a quota limit, so Claude Code never auto-continues it.
  - **Extend `stop-failure.ts`.** Today `planAlert` returns null on "(not your usage limit)" (`stop-failure.ts:276`). Instead, alert once per breaker opening (keyed on `since`) with the slot, since when, and the commands. On Linux the action is `gateway slot <slot> <other backend targets from the person's chains>`, reusing `suggestedTargets`. The body says "then send a message" (no watchdog) or "Claude Code goes on by itself" (watchdog on).
  - In a lead session, the monitor's line covers it.

### 2.4 What is not possible
- **The router alone cannot make a session wait 12 h.** Claude Code cuts a request with no headers after about 5 min. Without the watchdog it retries only 10 times, with each wait at most 60 s (more fails at once). [checked]
- **The router must not fake Anthropic's quota headers** to trigger auto-continue. Claude Code would show plan-limit and upsell messages, and `/usage` would mislead.
- **Auto-continue never covers subagents, background sessions or `-p`**, and only reacts to Anthropic's own usage limit. [checked]
- **A hook cannot start a new turn after an error**, because StopFailure's output is ignored. Only a monitor (in the lead) or the person can.
- **The kit cannot switch the Claude account or detect a switch reliably.** The person runs `/login` and says "go on". Whether a running process picks up the new login is [hunch].
- **A request waiting in the watchdog for a Claude reset sleeps until the reset.** It rechecks only "lifted early" through Anthropic. A model change (`gateway slot opus …`) reaches it only at its next attempt, or if a message wakes it [hunch: P-BR5].
- **The judge cannot hold.**
- **One login has one usage window.** No layer adds Claude capacity. Four Opus subagents and the lead still share it (D37).

## 4. Open questions for the owner, with my recommendation

1. **429 or 529 for the breaker's answer?** I recommend 429 with no quota headers, plus `x-should-retry: true` and a retry-after of 60 s or less.
2. **Hold length?** I recommend 240 s for streaming, 60 s for non-streaming, one global `timeouts.breakerHoldMs`, with 0 meaning "answer at once". Final value after P-BR1c.
3. **Breaker default per slot?** I recommend on for every slot except the judge. The judge never holds and cannot be turned on.
4. **May the judge hold?** I recommend no.
5. **Should setup turn on Claude Code's watchdog?** I recommend on by default in workers' own settings files, and an opt-in question (default no) for the person's own sessions.
6. **Where does "12 hours" live?** I recommend `workflow.limitWaitHours = 12` rather than `workflow.workers.retryHours`, since it also covers the person's own sessions.
7. **What happens after 12 h?** I recommend: stop waiting, mark the worker `failed` with the reason, and tell the lead and the person once. Please confirm this is what "after which the work goes on by itself" means: I read it as "goes on as soon as a model answers, within 12 h".
8. **Clamp every relayed backend retry-after to 60 s even with the breaker off?** I recommend yes; it is a bug fix.
9. **Hold the last target's heartbeat-only stream (180 s) while the breaker is on?** I recommend yes.
10. **How should a paused worker on an idle slot (no traffic) be probed?** I recommend resuming one canary worker rather than having the router or the CLI send a synthetic prompt. The fallback is a tiny `gateway probe <slot>` request sent straight to the backend.
11. **Detecting an account switch?** I recommend the explicit `worker resume --paused` (or telling the lead "go on"). Watching the credentials file's mtime is a later option, Linux only.
12. **Ship as a 0.7.x patch?** I recommend no: ship in 1.0.0, so every machine's router restarts only once.
