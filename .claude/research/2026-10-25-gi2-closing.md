# GI2 research: how GitHub closes an issue, and how the kit marks one fixed (2026-10-25)

Question: a fix merged into a release branch is not on the default branch. What closes its
issue, and what must the kit do at the merge and at the release (decision D67)?

## Sources (read 2026-10-25)

- Linking a pull request to an issue:
  <https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue>
- `gh issue comment`: <https://cli.github.com/manual/gh_issue_comment>
- `gh issue edit` (`--add-label`): <https://cli.github.com/manual/gh_issue_edit>
- `gh issue list` (`--label`, `--state`, `--json`): <https://cli.github.com/manual/gh_issue_list>

## What GitHub does

- **Nine closing keywords:** `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`,
  `resolves`, `resolved`. A colon may follow; case does not matter.
- **Syntax:** `KEYWORD #<n>` for the same repository. One keyword per issue: `Fixes #1, fixes #2`.
  The kit writes one `Fixes #<n>` line per issue.
- **Where:** in the pull request's description, or in a commit message.
- **Only the default branch closes.** A pull request description that targets any other branch:
  the keywords are ignored, no link is made, and merging has no effect on the issue. A
  keyword in a commit message closes the issue when that commit reaches the default branch.
- So: a crew merge into `release-<x>` (a local `git merge --no-ff` by the lead, or a pull request
  into a non-default base) closes nothing. The release pull request, into the default branch, is
  what closes. Its body must list the issues; the commits it carries may also, but a body line is
  the one that is visible and checkable.
- A closing keyword that the pull request does not carry closes nothing: it is not enough to
  label an issue. Hence the label `fixed-unreleased` is the kit's own memory of "fixed, waits for
  the release", and the release's `Fixes #<n>` lines are built from it.

## What the kit does with that

1. **At a crew merge** (switch on): one comment on each issue the phase fixes, and the label
   `fixed-unreleased`. No closing keyword in the comment: the comment is not a pull request, and
   a keyword in it would be inert anyway.
2. **At the release:** `issue fixed --base <default> --head <branch>` lists the issues that are
   open, carry `fixed-unreleased`, and whose comment names a commit that is in
   `<default>..<branch>`. The pull-request skill pastes one `Fixes #<n>` line per issue.
3. **GitHub closes the issues** when that pull request merges into the default branch. The label
   stays on the closed issue: harmless, and it shows the issue shipped through the kit.

## Choices

- **How the kit remembers a merge was marked:** the comment carries a hidden marker with the
  issue, branch and commit (`<!-- cc-smart-dev-kit:fixed <branch>@<commit> -->`). Before a comment is
  posted the issue's comments are read; a marker already there means done. This survives a
  restart of the watch and a second place seeing the same merge. A GitHub failure leaves nothing
  recorded, so the next pass tries again.
- **Which commit:** the merge commit, or the branch tip when the merge was a fast-forward, short
  (`--abbrev`). The range check in `issue fixed` uses the commit named in the marker.
