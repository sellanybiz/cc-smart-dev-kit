## How the proofs ran

- A **fake Anthropic server** per settings source: a Bun script on a free local port (never
  20100, the live router's), answering `HEAD /api/hello`, `POST /v1/messages` (JSON and SSE) and
  `POST /v1/messages/count_tokens`, and logging every request's method, path, headers, body size
  and model, and whether the body held a marker string. Credentials in the log are noted only as
  present.
- A **throwaway `CLAUDE_CONFIG_DIR`** for every run but P1 (no login, no history of the person's),
  a fake API key, `--strict-mcp-config`, `--model haiku --effort max`. `HOME` was not changed, so
  the person's global `CLAUDE.md` was still read by every session — the interactive runs showed its
  external-imports prompt — while the config folder kept settings, trust records and transcripts
  away from the real config.
- **No request reached the real Anthropic API**: the model traffic went to the fake server. Claude
  Code's own background traffic still left the machine — its changelog and closed-issues fetch (a
  1 MB `cache/changelog.md` appeared in the throwaway config), and in P1 the kit's own update check
  among the real config's SessionStart hooks (its log says "up-to-date: 1.1.1" at the minute of the
  run). "Against a fake Anthropic" is the right phrase, not "offline".
- Never the person's settings files, never this repo's `.claude/settings*.json`, never the live
  router. P1 alone used the real config folder and the real login, for one tiny request.
- Scripts and logs live in the lead's job folder (`~/.claude/jobs/<job>/tmp/r6/`), not in the
  repo.

The run shape, per case (the settings files and `--settings` change as the case needs them):

```sh
cd <the folder under test>
CLAUDE_CONFIG_DIR=<throwaway config> ANTHROPIC_API_KEY=<fake> ANTHROPIC_BASE_URL=<the shell's server> \
  timeout 120 claude -p --model haiku --effort max --strict-mcp-config 'Say ok'
```

- Each proof is one or more such runs, except P10 (five `claude --bg` starts) and P9 and P13's Esc
  case (interactive sessions in a private tmux server) — the status line is an interactive feature,
  and `-p` has no trust dialog.

## P1 — an explicit `https://api.anthropic.com` keeps the claude.ai login

**Setup.** The person's own config folder (the saved claude.ai login), a new empty folder, and a
`--settings` file of the proof's own setting only `env.ANTHROPIC_BASE_URL=https://api.anthropic.com`
(the person's own settings set it to the local router, `127.0.0.1:20100`). Prompt `Say ok`; one
request.

```
claude -p --model haiku --effort max --strict-mcp-config --settings <file> \
  --output-format stream-json --verbose 'Say ok'
```

**Seen.** Exit 0. The stream's init line read `apiKeySource: "none"`, `model:
"claude-haiku-5-5"`, `permissionMode: "auto"`. The result line read `subtype: "success"`,
`is_error: false`, `result: "ok"`, `total_cost_usd: 0.00399`, `terminal_reason: "completed"`, and
no stderr.

**Verdict: proved.** No API key was in play (`apiKeySource: "none"`) and the answer came back, so
the saved claude.ai login authenticated the request to Anthropic's own URL.

**Means.** GP2's "off" state — an explicit `https://api.anthropic.com` — keeps the person's normal
login; turning the gateway off does not log them out. GP3's `--no-gateway` can pass that value
through `--settings` the same way.

## P3 — the settings chain: `--settings`, then the project's two files, then the user file

**Setup.** Fake servers, one per settings source, in a trusted folder. First set: the project's
`.claude/settings.json` → A, its `.claude/settings.local.json` → B, the `--settings` file → C, the
shell export → D. A second set, run after the review pointed out the gap, puts the **user**
settings file against the project's files: user → B2, shared → H, local → C2, shell → G. One
`claude -p --model haiku --effort max` per case.

**Seen.**

| Run | Sources in play | The message request reached |
|---|---|---|
| 1 | `--settings` C, local B, shared A, shell D | **C** |
| 2 | local B, shared A, shell D | **B** |
| 3 | shared A, shell D | **A** |
| 4 | shell D | **D** |
| 5 | user B, `--settings` C, shell D | **C** |
| 6 | user B2, shared H, shell G | **H** |
| 7 | user B2, local C2, shell G | **C2** |
| 8 | user B2, shared H, local C2, shell G | **C2** |

**Verdict: proved.** On 2.1.309 the order for an `env` key is `--settings` > `settings.local.json`
> `.claude/settings.json` > the user file > the shell. Every settings file beat the shell's export;
the shell's value applied only when no file set the key.

**One detail the router should know.** The startup `HEAD /api/hello` did **not** follow a project
or local file: with `--settings` it used that file's URL; when the URL came from the user settings
file, it used that; when only a project or local file named the URL, it used the **shell's** value.
The message requests followed the settings chain. So a health probe can reach a different URL than
the requests of the same session.

**Means.** GP2 writes the project's state to `settings.local.json`: it beats the team
`.claude/settings.json` and the user file (where `gateway on` writes today), and only a
`--settings` file (GP3) beats it — as designed.

## P4 — a settings file's `env` beats a shell export

**Setup.** The shell exported a base URL (D) in every run; the URL came from one file at a time.

**Seen.** With the local file B and the shell D, the request reached B; with the project A and the
shell D, A; with the user file B and the shell D, B; with no file at all, D. A `--settings` file C
against the shell D reached C (P3's first run).

**Verdict: proved.** Any settings file that sets the variable wins over the shell's value.

**Means.** GP3 must pass its `env` through `--settings`, as the design says. A launcher that set
the URL as an environment variable — the way `ollama launch claude` does — would lose to any of
the person's settings files.

## P5 — a path in `ANTHROPIC_BASE_URL` is kept

## P6 — the local file is the main checkout's; the shared file is the starting folder's

**Setup.** A temp git repo (the main checkout) with `.claude/settings.json` → A and
`.claude/settings.local.json` → B; a subfolder; a linked worktree cut from the repo; the shell →
D.

**Seen.**

| Session started in | Its own `.claude/` | The message request reached |
|---|---|---|
| main checkout root | local + shared | B |
| subfolder | none | B (the main root's local) |
| subfolder | `settings.local.json` → C | B (its own local ignored) |
| linked worktree | none | B (the main root's local) |
| linked worktree | `settings.local.json` → C | B (its own local ignored) |
| main root, local removed | shared only | A |
| subfolder, local removed | shared only at the main root | D (the root's shared file is **not** read) |
| subfolder | its own `settings.json` → C | C |
| linked worktree, shared untracked in the main root | none | D (the worktree has no such file) |
| linked worktree, shared committed and merged in | `settings.json` → A | A |

**Verdict: proved, as the docs say.** `settings.local.json` is read at the **main checkout's
root** for the checkout, for every subfolder and for every linked worktree; a local file anywhere
else is ignored. `.claude/settings.json` is read from **the folder the session starts in**: a
subfolder does not see the checkout root's shared file, and a worktree sees the shared file only
when it carries it (committed). An untracked local file in the main checkout did not appear in the
worktree, which is why the person's own file must stay ignored (the design's managed
`.git/info/exclude` line does that).

**Means for GP2 and GP4.** The personal file at the main checkout's root is the one that reaches
**every** session of the project — the checkout, its subfolders and its worktrees. The team file
written at the main root is **not** read by a session started in a subfolder, so a team "off" or
"default" state would not apply there; the team half of the design has that limit, and GP2 must
accept it or write the team state somewhere a subfolder reads. Worktrees do read a committed team
file. GP4's effective-state reader must look for the local file at the main checkout's root, not
beside the session's `cwd`.

## P7 — a changed value reaches a running session; a removed key waits for a restart

**Setup.** One long-lived `claude -p` per run, with stream-json input and output, driven by a
small Bun script that rewrites the settings file between turns:

```
claude -p --input-format stream-json --output-format stream-json --verbose
```

The project's `settings.local.json` first named B, then C, then held no `env` key at all; the shell
named D.

**Seen.** With 112 ms between the write and the next turn, the turn still went to **B** (the old
value). With 1 s it went to **C** (a later run: the write at `10:17:45.504`, the turn's POST at
`10:17:46.966`), and the following turn too; with 3 s, likewise (the first run). The changed value
reached the running session with no restart. After the key was removed, and 3 s later, the next
turn still went to **C** — the removed key never reached the session, which kept the old value. A
fresh session with the key gone fell to **D**. The same held for the user settings file (B, then
C).

**Verdict: proved**, with a timing detail: a settings watch applies a changed value within about a
second — 0.112 s was too early, 1 s was enough — and a removed key is never applied.

**Means for GP5.** `gateway off` must **set** `https://api.anthropic.com` instead of removing the
key: a set value reaches a running session within about a second, while a removed key does not
reach it at all (the session kept the router's URL). GP5's design is right. For GP2: a project's
state change reaches the project's running sessions within about a second.

## P8 — a project's `env` does not wait for trust in `claude -p`

**Setup.** A fresh config folder with **no trust record**. Two never-trusted folders: one with
`.claude/settings.json` → A, one with `.claude/settings.local.json` → B; the shell named D. Then
the same folder again after a trust record was added.

**Seen.** Both folders' `env` applied in `-p`: the request reached **A** and **B** respectively,
with no trust record anywhere, and the session said nothing about trust (stdout, stderr). Adding
the trust record changed nothing. Separately, `claude --bg` in a never-trusted folder refused to
start: exit 1, stderr `Workspace not trusted. Run \`claude\` in <folder> once and accept the trust
prompt, then retry.` (P10.)

**Verdict: refuted for `-p`.** The brief's claim — and the docs' trust rule — hold for the
interactive session and for `--bg`, but not headless: `claude -p` applies a project's or local
file's `env` in a folder that was never trusted, silently. (The interactive trust dialog was not
re-observed here; the interactive runs used a trusted folder.)

**Means for GP2 and GP3.** A headless session (`-p`) and a crew session (`--bg`) behave
differently: the project's state applies for `-p` with no trust, while `--bg` refuses without it.
A launcher that starts background sessions in a project folder must make sure the folder is
trusted — the crew start already depends on that. For an interactive start, the person sees the
trust dialog before the project's state takes effect (the docs; not re-observed).

## P9 — the status line sees the session's effective base URL

**Setup.** Interactive sessions in a private tmux server, with a status line command that dumps
its own environment (`env`) to a file. Twice: once with the URL from a `--settings` file, once with
it from the **project's** `settings.local.json`; the shell exported a different URL in both, and an
`apiKeyHelper` supplied the fake key — in the `--settings` file in the first run, in the user
settings file in the second.

**Seen.** The status line ran in both sessions, and `ANTHROPIC_BASE_URL` in the dump was the
**effective** URL — the `--settings` file's in the first run, the project local file's in the
second — never the shell's. `CLAUDE_CONFIG_DIR` and `PWD` were there; no key variable was.

**Verdict: proved.** The status line command gets the session's effective `ANTHROPIC_BASE_URL`,
including one that comes from a project's local file.

**Means for GP4.** A status line can show the gateway state the session really uses per project,
by reading `ANTHROPIC_BASE_URL` from its own environment — not by reading the settings files
itself. `doctor`, `restore` and the portal's Gateway card still read the files through the one
effective-state reader (GP2); the status line is a faithful per-session view beside them.

## P10 — `--settings` carries over to a background session

**Setup.** A trusted folder in a throwaway config, a `--settings` file naming C (and carrying a
fake key through `apiKeyHelper`), the shell naming D (with no key), `claude --bg --settings <file>
'Say ok'`.

**Seen.**
- Untrusted folder: exit 1, `Workspace not trusted. Run \`claude\` in <folder> once and accept the
  trust prompt, then retry.` — no session.
- Trusted folder: `backgrounded · <id>`; the session's startup `HEAD /api/hello`, its model
  request (Opus 5.5) and three small haiku requests all reached **C**, none reached the shell's
  D; the session's log showed the answer `ok`.
- A key in the **caller's** environment did not reach the session (it ended "Not logged in"), and
  neither did an `ANTHROPIC_API_KEY` in the settings file's `env`; the settings file's
  `apiKeyHelper` did. (No run had a login in the throwaway config folder, so whether a real login
  there is the other route is inferred, not shown; the caller's-environment clause rests on these
  runs.)

**Verdict: proved** — the file's `env` (the URL) and its `apiKeyHelper` reach a `--bg` session, and
its requests go where the file says. A `--bg` start needs a credential the settings chain can
supply (a real login, or an `apiKeyHelper`), not a key in the caller's environment.

**Means for GP3 and the crew.** `launch --bg` and the crew start can rely on `--settings`: the URL
and the other `env` keys reach the background session. A machine whose login lives in the person's
config is fine; a test rig needs an `apiKeyHelper`.

## P12 — no request header names the project

**Setup.** A session in a folder with a unique name (`r6proj-a7f31c`) against a fake server that
logs every header, and says whether a marker string appears in a header or in the body and in
which field of the body.

**Seen.** Two requests (`HEAD /api/hello`, `POST /v1/messages?beta=true`). The POST's headers:
`accept`, `accept-encoding`, `anthropic-beta`, `anthropic-dangerous-direct-browser-access`,
`anthropic-version`, `connection`, `content-length`, `content-type`, `host`, `user-agent`, `x-api-key`,
`x-app`, `x-claude-code-session-id`, `x-stainless-arch`, `x-stainless-lang`, `x-stainless-os`,
`x-stainless-package-version`, `x-stainless-retry-count`, `x-stainless-runtime`,
`x-stainless-runtime-version`, `x-stainless-timeout`. **No header value held the folder's name or
its path.** The body did: a second run that logged the body's fields found the marker in the
**system prompt** — the text `Primary working directory: <the folder>` — and in a message of the
same request; not in `tools`, not in `metadata`. The body's `metadata` held `device_id`,
`account_uuid` (empty under a fake key) and `session_id`, no project.

**Verdict: proved.** The router cannot tell projects apart from a request header; the prefix is
the only reliable discriminator it gets. The body does name the project's path, so a router
*could* parse it — the design must not: it is fragile (a `cd`, a linked worktree) and it is the
person's own file layout.

## P13 — a cancelled request closes the connection; nothing else arrives

**Setup.** A fake server that holds the answer (never sends a body) and logs when the caller goes
away. Two cases: SIGINT to a `claude -p` while its request was held, and Escape in an interactive
session while its request was held.

**Seen.** (The script sent the signal or the key as soon as it saw the request, so the delay from
request to abort is its own polling; what the proof shows is what followed.)
- SIGINT, run twice: the wrapper exited 130; the server logged `request_signal_aborted` (Bun's
  request signal) and, within 0.11 s, `client_closed` with `AbortError: The connection was closed.`
  — 0.38 s after the request the first time, 2.0 s the second (the second run's log is kept in
  the job folder as `log-F2.jsonl`). No further request came from that session.
- Escape: the same two events, 0.27 s after the request; the interactive session stayed alive and
  its pane returned to the prompt.
- In the Escape run, two more requests appear four seconds later: the interrupted prompt was back
  in the input box, and the driver's `/exit` keystrokes were appended to it and submitted — the
  large one is that stray message (81,352 bytes against the held request's 81,347: five bytes
  longer, the length of `/exit`); the small haiku call beside it (4 KB, no tools) is one of Claude
  Code's side calls. Neither is a retry of the cancelled request.

**Verdict: proved.** A cancelled request is a closed connection: `request.signal` aborts and the
response stream's `cancel` runs. No cancel request, no header, nothing else arrives. A `-p` run
ends with 130.

**Means for the router.** Abort the upstream request when the client connection closes (Bun gives
both the request signal and the response stream's `cancel`), and treat a closed connection as "the
person cancelled", not as a failed answer to retry.
