# Slop audit 2: copies of shared homes and bypassed homes

Base: main at ebaf2a92 (plugin 6.7.1). Audited for: a copy of code, text or a type that a shared home in this repo already holds, or code that goes around a shared home (a bypassed home or a drifted copy). Judged by code-structure §§ 3, 4, 5, 11 and 13 and `.claude/rules/dynamic.md`. Scope: `src/cli`, `src/setup`, `src/gateway`, `src/portal` (not `src/portal/api/`), `src/worktrees`, plus `src/hooks/settings-hooks.ts`, `src/hooks/playwright-output.ts`, `src/hooks/after-merge.ts`, `src/jobs/package-scripts.ts`, `src/herdr/machines.ts`, `src/omniroute/install.ts`. The repo's review add-on has no Reuse signals commands, so no guard output seeded the run. The first audit (`.claude/audits/2026-11-26-slop-homes.md`) covered other folders.

Several auditors reported the same defect; each is merged below into one section. Each finding was confirmed by a separate check in the code. The worktree `.claude/worktrees/field-fixes` named in the brief did not exist for the checkers, so they read the main checkout.

## Confirmed findings (most severe first)

### 1. `loadConfigFile` reads the hand-edited `gateway.json` with plain `JSON.parse`, beside `parseUserJson`

- Where: `src/gateway/config.ts:903` (`loadConfigFile`, lines 886-912). The same defect is in `src/cli/migrate.ts:759` (`readOldConfig`, the other reader of the same file).
- Trigger: a person edits `~/.config/cc-smart-dev-kit/gateway.json` in an editor that saves UTF-8 with a byte order mark (BOM), such as Windows Notepad. The file is meant to be edited by hand: the error text says "Fix it by hand", `docs/gateway.md:1714` says "A bad edit keeps the last good config", and `README.md:1254` and `docs/gateway.md:1331` send people into the file to set `history.retentionDays` (no command sets it). On Windows `isOwnerOnly` never refuses the file, so it reaches line 903. `readFileSync(..., "utf8")` keeps U+FEFF and `JSON.parse` throws (probed in bun).
- Outcome: `loadConfigFile` throws `ConfigError` "<path> is not valid JSON. Fix it by hand." for a file that looks valid. About 20 non-test call sites go through it (gateway commands, doctor, project-state, portal facts and actions, session-facts, claude-mem). The router's watcher uses it as `REAL_WATCH_DEPS.load` (`config.ts:961`): a running router keeps its last good config, but after a restart it has none and runs on `emptyConfig()` with every slot off. `gateway/settings.ts:205` reads Claude's settings with `parseUserJson`, so two gateway readers disagree on the same kind of file.
- Missing guard: `src/setup/user-json.ts` calls itself "the one home of that read, so every reader agrees", and `docs/windows-setup.md:126-132` says every reader of a person-edited JSON file goes through it. The sibling kit config `src/jobs/config.ts:104` already does, with a BOM test (`config.test.ts:71`). The 6.7.1 fix covered only `workflow/resolve.ts`. No test covers a BOM `gateway.json`.
- Fix: `parseUserJson(readFileSync(path, "utf8"))` at `config.ts:903` (keep the error text), and the same in `migrate.ts` `readOldConfig`. `config.ts` already imports from `../setup/`. `config.ts` is in the router bundle (`plugin/dist/router.js` has 0 uses of `parseUserJson` today), so the fix changes that bundle and needs a deliberate release (`bundles-and-releases.md`). Correction to one auditor claim: setup's managed writers do not write this file (`saveConfig` uses `atomicWrite`).

### 2. Doctor's `hooksOf` and `baseRefOf` read project settings with plain `JSON.parse`, beside `readUserJson` in the same command

- Where: `src/hooks/settings-hooks.ts:73` (`hooksOf`) and `src/cli/project-checks.ts:417` (`baseRefOf`).
- Trigger: a project's `.claude/settings.json` or `.claude/settings.local.json` is saved with a BOM. Claude Code reads it fine (`user-json.ts:7-8`). Both functions catch the parse error and return null.
- Outcome: `wiredHandlers` and `allWiredHandlers` return `[]`. Doctor's `engineLines`, `oldNameLines` (`project-checks.ts:324,348`) and `ownCopyLines` (`:526,:562`) go silent: a leftover retired-engine hook line goes unreported, and a project that replaced a plugin hook gets the false warning "the project's settings wire no hook on <event>: nothing answers in its place. Take <name> out of ownHooks". `baseRefOf` stays null, so doctor warns (`:397`) that the settings do not set `worktree.baseRef` head when they do. `project init` reads the same files through `parseObject` -> `parseJsonObject` -> `parseUserJson` (`init.ts:206-209`, `managed-json.ts:202`), so it sees and removes lines doctor never reported, and finds `baseRef` already set while doctor says to add it. `src/update/retired-repos.ts:107` reads `cc-smart-dev-kit.json` through `parseUserJson` but `:114-116` reads the same project's settings through `allWiredHandlers`, so one feature disagrees with itself; a BOM repo with retired engine lines is skipped silently. Probe (temp folder, deleted): on a BOM file `allWiredHandlers` returned `[]` and `readUserJson` found the hook.
- Missing guard: the same `user-json.ts` one-home claim, `docs/windows-setup.md:126-132`, and the comment at `src/cli/doctor.ts:139-142` ("setup and doctor can never disagree about a key"). `project-checks.ts` already imports `parseUserJson` and `readUserJson` (`:95`) and uses them at `:150,:185,:601,:727,:828,:860`. No BOM test exists for either function. The comment at `settings-hooks.ts:80` ("Claude Code cannot run its hooks either") does not hold for a BOM file.
- Fix: `parseUserJson(readFileSync(file, "utf8"))` in `hooksOf`; `parseUserJson` or `readUserJson` in `baseRefOf`. `user-json.ts` imports only `node:fs` and no zod, and `retired-repos.ts` already imports both files, so no zod-free hook gains zod. Corrections to the auditors: `retiredReviewAgentCheck` (`:150`) does not read the settings file (it gets `cc-smart-dev-kit.json` and `workflow.json`), and the "ownHooks double run" only happens if the person follows the false warning.

### 3. The job classifier reads `package.json` with plain `JSON.parse`

- Where: `src/jobs/package-scripts.ts:60` (`scriptsOf`) and `:100` (`packageJsonAt`).
- Trigger: a project's `package.json` is saved with a BOM. A session runs `bun run build`, and `job-route` classifies it. Both calls throw and the catches return null. Probe: `packageScripts` returned null for a BOM file and the scripts map for the same file without the mark.
- Outcome: null means "the word is the tool of that name" (`package-scripts.ts:9-12`, `classify.ts:153-164` caches the null, `:446-465`). A heavy script (`build` = `next build`) is judged by its name, not its body, so the queue may not hold it. `usesYarnBerry` is never consulted for that folder, so its `packageManager` lookup is lost too. `project-checks.ts:828` and `:860` already read `package.json` through `parseUserJson`, so doctor and the queue read the same file two ways.
- Missing guard: `user-json.ts` one home (code-structure § 5). No BOM case in `package-scripts.test.ts` or `classify.test.ts`.
- Fix: `parseUserJson` at `:60` and `:100`. The cost is lower than an auditor feared: `plugin/dist/job-route.js` already bundles `withoutBom`, `parseUserJson` and `readUserJson` (lines 158-164), so the hook bundle does not grow. One side claim is not proved: that npm, yarn or bun accept a BOM `package.json` (one auditor's probe said `bun run` does; the checker's probe was denied). The defect does not depend on it.

### 5. Three blocking `gh` spawns re-spell `runGh` without `windowsHide`, with copies of `GH_TIMEOUT_MS` and `ghMissing`

- Where: `src/worktrees/scan.ts:279-295` (`pullRequestState`), `src/hooks/after-merge.ts:1216` (`readGhAliases`) and `:1527-1535` (`viewPullRequest`); homes: `src/workflow/merge-check.ts:55` (`GH_TIMEOUT_MS`), `:108-117` (`runGh`), `:580` (`ghMissing`).
- Trigger: on Windows, the detached background `worktrees clean` (`auto-start.ts:99`) calls `pullRequestState` per branch, and the after-merge hook runs `gh alias list` and `gh pr view` on a merge line.
- Outcome: `runGh` sets `windowsHide: true` with the comment "A guard runs with no console of its own on Windows: without this, gh opens one". `hooks/git.ts:134,:167`, `project/locate.ts:149,:185` and `hooks/detached.ts:199` do the same. None of the three gh spawns does, so each can open a console window on Windows (not run on Windows; the claim rests on the project's own comment, and `docs/claude-code-contract.md:130` notes hooks start with `windowsHide: true`, so it is unproved at runtime). The 10 s timeout is typed three times: `merge-check.ts:55` (exported), `scan.ts:240` and `after-merge.ts:1178`, whose comment "both hooks allow a gh call 10 s" is stale. `scan.ts:279` repeats the body of `ghMissing`. A change to the gh recipe or limit needs four edits.
- Missing guard: `.claude/rules/dynamic.md` ("Ports, timeouts, budgets and limits are one named constant"), code-structure §§ 3, 5, 11. The note at `merge-check.ts:100-101` ("a few blocking reads ... still spawn gh themselves") admits the debt; it is not a rule that allows it. `runGh` is async only.
- Fix: a blocking twin of `runGh` in a zod-free module next to `hooks/git.ts` (after-merge must not import `merge-check`, which pulls `./resolve` and zod, `hooks.md`), holding `GH_TIMEOUT_MS`, the spawn options with `windowsHide`, and the `ghMissing` test; re-export from `merge-check.ts`; import it in `scan.ts` and `after-merge.ts`. `scan.ts` already imports zod, so it has no bundle limit.
