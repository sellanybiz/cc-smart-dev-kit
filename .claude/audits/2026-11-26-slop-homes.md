# Audit: copies and bypassed homes in src/tasks, src/herdr, src/workflow, src/project and src/hooks/git.ts

Base: main at 0882d5db. Read-only audit. Judged by code-structure §§ 3, 4, 5, 11 and 13 and by `.claude/rules/dynamic.md`. This repo's review add-on has no Reuse signals commands, so no guard output seeded the run.

Seven confirmed findings, most severe first. Duplicate reports of one defect are merged. Each was checked in the code by a verifier; corrections the verifier made to the original claim are stated inside the finding.

## 1. The person's workflow.json is read with plain JSON.parse; every other reader of a hand-edited file uses parseUserJson

- Where: `src/workflow/resolve.ts:156` (`parseWorkflowText`); also `src/workflow/resolve.ts:289` (`statusLineIsOurs`, same class).
- Trigger: a person on Windows saves `~/.config/cc-smart-dev-kit/workflow.json` in Notepad, which writes UTF-8 with a byte order mark (BOM). `loadWorkflow` (resolve.ts:168-177) reads it and `parseWorkflowText` calls `JSON.parse(text)`. The hook cache reads the same file through the same function (`src/entries/config-check.ts:51-54`). A probe with a BOM file made `loadWorkflow` throw "not valid JSON (JSON Parse error: Unrecognized token)", while `readJsonObject` parsed the same file.
- Outcome: `workflow show`, `resolveWorkflow`, `resolvePlans` and `resolveAlerts` throw `WorkflowConfigError`. The hooks do not fail closed: `loadPersonalWorkflow` (`src/hooks/checked-config.ts:262-279`) turns the failure into `{}`, so a hook silently drops the person's defaults (for example `switches.jobRoute`, `switches.leadHint`). `workflow set` reads the same file with `readJsonObject` (`src/workflow/write.ts:143`), which skips the BOM (`src/setup/managed-json.ts:196-205`), so the write path accepts a file the read path refuses. At `resolve.ts:289` a BOM in `~/.claude/settings.json` makes the status-line switch read as off.
- Missing guard: `src/setup/user-json.ts` says it is "the one home of that read, so every reader agrees". About 30 readers use it, among them `jobs/config.ts:42,104`, `project/config.ts:597` and `gateway/settings.ts:205`. Nothing fails on a plain `JSON.parse` of a hand-edited file (code-structure § 5, copies that drift).
- Fix: `raw = parseUserJson(text)` in `parseWorkflowText`, and the same in `statusLineIsOurs`. The config-check bundle already carries user-json through `project/config.ts`, so there is no size cost.

## 2. createPullRequest starts gh by hand though runGh is documented as the one place the kit starts gh

- Where: `src/workflow/propose.ts:482-512` (spawn at 489, signal rule at 503). Third copy: `src/cli/project-init.ts:120-139` (async `runGh`, plus a sync twin at 141-155).
- Trigger: any `workflow propose` run that reaches `createPullRequest`. It calls `Bun.spawn(["gh", ...args], { cwd, env, stdin: "ignore", stdout/stderr: "pipe", timeout, windowsHide: true })` and reads both streams plus `exited`. That is the same spawn and read as `runGh` (`src/workflow/merge-check.ts:92-130`). `propose.ts:55` already imports `GH_TIMEOUT_MS`, `ghMissing` and `spawnGh` from `./merge-check`.
- Outcome: the copies have drifted. `runGh` counts only SIGTERM as a timeout (merge-check.ts:110-111) and reports a missing gh as `kind: "missing"`; `createPullRequest` counts any signal as `timedOut` and reports a missing gh as a bare spawn-error text; the project-init copy has no `windowsHide`, so gh opens a console window on Windows. The comment at merge-check.ts:84-87 ("The one place the kit starts `gh`") and `docs/design/issues.md:119` are false. A change to the gh contract must be made in three places. The claim was false when written: `createPullRequest` came first (a5341714), then the claim (99142e6d). Other hand-written gh spawns exist outside the audited folders: `src/worktrees/scan.ts:282`, `src/hooks/after-merge.ts:1216` and `:1529`.
- Weaker than first stated: a missing gh is mostly caught earlier by `ghLoginState` and `ghMissing` (propose.ts:135-141, 641-646), so the raw spawn-error text shows only if gh vanishes between the two calls.
- Missing guard: nothing fails on a second gh spawn (code-structure § 11, "a claim with no guard"; § 5).
- Fix: `createPullRequest` calls `runGh(args, { env, folder: repo, timeoutMs })`. Map `code === null` (any signal) to `timedOut`, not only `kind === "timeout"`: propose.ts:753-781 keeps the pushed branch on `timedOut` because the pull request may exist, and that safety must stay. Move project-init's async `runGh` onto the same runner.

## 3. "The commit this name resolves to" is spelled by hand in six places beside commitArgs/commitIn

- Where: `src/tasks/stack-proof.ts:65` (`branchTip`), `:77-82` (`defaultTip`), `:92` (`commitOf`); `src/tasks/plan-guards.ts:304` (`staleBriefWarning`); `src/tasks/deploy/branch.ts:38` (`knowsRef`) and `:401-403` (`readGitFacts`, which repeats the question although `knowsRef` is in the same file). One more exact copy outside the area: `src/issues/fixed.ts:357-358`.
- Trigger: `src/hooks/git.ts:188-199` holds `commitArgs` (`rev-parse --verify --quiet <rev>^{commit}`) and `commitIn` (checks `COMMIT_SHA`). Commit e670f582 (2026-11-26) named them "the one home for the commit a rev names" and moved files-check, workflow, review-record and review-cover onto them, but left these older copies. `StackGit` is `(args) => GitRun`, and `src/herdr/plans.ts` already shows both spellings over one runner: `baseRef` (175-180) uses `commitIn(git(world, commitArgs(ref)))` and `tipOf` (183-185) calls the hand-spelled `branchTip`.
- Outcome: drift, not a live bug. The accept rules differ (`COMMIT_SHA` against `out !== ""`); `branch.ts` adds `--end-of-options`, `commitArgs` does not; `stack-proof.ts:91` and `issues/fixed.ts:357` each add their own `startsWith("-")` guard. A change to the lookup must be made in about six places. Verified not a bug today: because `^{commit}` is always appended, a name starting with a dash exits 1 on git 2.53, and `herdr start --base -x` is refused earlier (`src/herdr/words.ts:183-184`), so it never reaches git as an option. Also, a successful lookup always prints a full id, so `out !== ""` and `COMMIT_SHA` accept the same answers.
- Not copies: `refCommit` (`branch.ts:25`) leaves out `--quiet` on purpose so git's error reaches `unreadableRefMessage`. `branch.ts:379`, `:403` and `ops.ts:1017` ask a different question (no `^{commit}`).
- Missing guard: no test or lint fails on another spelling (code-structure §§ 3, 5, 11).
- Fix: `commitIn(git(commitArgs(ref)))` in stack-proof's three lookups; `plan-guards` keeps its `GitRun` for the `code === 1` test and uses only `commitArgs`; `knowsRef` and `readGitFacts` share one call. Decide once whether `commitArgs` gets `--end-of-options`, and drop the per-copy dash guards if it does.

## 5. "Is this path inside the checkout" is written five ways, and one copy drifted

## 6. The deploy-task reader spawns git show by hand beside runGitRaw

- Where: `src/tasks/deploy/branch.ts:163-173` (`tasksOn`); callers at `:251` and `:264`.
- Trigger: each task blob is read with its own `Bun.spawnSync(["git", "show", `${commit}:${file}`], { cwd, env: { ...gitEnv(process.env), GIT_TERMINAL_PROMPT: "0" }, stdin, stdout, stderr, timeout, windowsHide })`. Its only stated reason is the comment "runGit trims stdout". `runGitRaw(cwd, args, env, timeoutMs, own)` (`src/hooks/git.ts:58-66`) returns stdout untrimmed through the same `spawnGitBytes` ("The one blocking spawn of git", git.ts:116-143) and takes `own`, so `{ GIT_TERMINAL_PROMPT: "0" }` can be passed. `runGitRaw` arrived 2026-11-12 (7cdab024), five days before the comment (7e6890b2), and the sibling `src/tasks/files-check.ts:14,120` already uses it. `branch.ts` already imports `runGit` from the same module.
- Outcome: the spawn recipe lives in two places. A fix to `spawnGitBytes` never reaches this call. A timeout throws "git show failed: " with empty stderr instead of the shared "timed out", and a spawn error is thrown raw instead of coming back as `ok: false`. Overstated in the first report: `tasksOn` takes no env parameter and its `refCommit` and `taskGit` calls also default to `process.env`, so a caller's env is not ignored here; and a missing git already throws earlier in `refCommit`.
- Missing guard: code-structure § 11 (a copy of a shared home) and core.md "One home for everything". Nothing fails on a second git spawn in `src/tasks`; this is the only one in that folder. Other hand-written git spawns exist elsewhere and are files of the same shape (`project/locate.ts`, `gateway/project-state.ts`, `update/check.ts`, `setup/marketplace-access.ts`).
- Fix: `runGitRaw(repo, ["show", `${commit}:${file}`], process.env, RESOLVE_GIT_TIMEOUT_MS, { GIT_TERMINAL_PROMPT: "0" })`, throwing with `result.err` on `!ok`.

## 7. herdr's leftBehind hand-copies branchTip, which the same file already imports

- Where: `src/herdr/command.ts:465-467` (`leftBehind`); caller `:524` inside `followupGate`.
- Trigger: a follow-up child's worktree is gone, so `tip ??= [`refs/heads/${branch}`, `refs/remotes/origin/${branch}`].map((ref) => commitIn(runGit(repo, commitArgs(ref), ctx.env))).find((commit) => commit !== null)`. That is `branchTip` (`src/tasks/stack-proof.ts:63-69`): same two refs, same order, first commit wins. `command.ts` imports `branchTip` at line 12 and calls it at line 983; `herdr/plans.ts:182-184` wraps it as `tipOf`.
- Outcome: two copies of "the commit a recorded branch is at, here or on origin" in one package. They already differ a little: this copy uses `COMMIT_SHA` through `commitIn`, `branchTip` accepts any non-empty answer, and `.map(...).find(...)` runs git for both refs where `branchTip` stops at the first hit. If the lookup changes, the start path follows `branchTip` while the follow-up gate that decides whether a gone child lost work keeps the old rule. No wrong behaviour today.
- Missing guard: code-structure § 5 and § 11.
- Fix: `tip ??= branchTip((args) => runGit(repo, args, ctx.env), branch) ?? undefined`.
