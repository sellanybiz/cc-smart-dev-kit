# Plan: 4.3.1 — fix the Herdr live-proof bugs (remote included)

## Summary

The live proofs for Herdr session orchestration (task #273) found seven bugs in `src/herdr/command.ts`.
4.3.1 fixes all seven: `answer` relays long permission prompts and single questions, `adopt` agrees with
`report` on "the lead is gone", `start` catches a child that dies at launch, independent and remote
sessions show in Herdr's window, and a remote start finds `claude` and the kit through the login shell.

## Context

Task #290 lists the bugs. Task #273's notes hold the live evidence: screens, status messages and the
commands that ran (hc 0.1.20, Claude Code 2.1.322, kit 4.3.0). 4.3.0 is merged and released, so this
is a patch release. Two remote proofs (item 8, remote start; item 9, an independent session's

## Research (facts proved live, 2026-11-12)

- **Remote PATH (vps, owner-run probes).** `hc exec --on` runs argv with a bare PATH
  (`/usr/local/bin:/usr/bin:…:/snap/bin`): no `claude`, no kit, no `bun`; only `node`.
  `"$SHELL" -lic 'command -v …'` finds `~/.local/bin/claude`, `~/.local/bin/cc-smart-dev-kit` and
  `~/.bun/bin/bun`. `hc run --on m '<one line>'` runs the line through plain `sh` (`$0 = sh`) with the
  same bare PATH, so `command -v claude` fails (exit 127). `hc exec` has `--env`; `hc run` has
  none. Neither helps, since the remote login PATH is not known on this side.
  `SHELL=/bin/bash` is set under `hc exec` on vps.
- **The planned launch, proved by hand on vps (owner-run):** `hc run --on vps --bg
  --keep --no-parent --no-notify --name kit-rprobe --label herdr.space=sp… --label herdr.tab=tb… --
  sh -c '<wrapper>' kit claude …` gave `vps/t29`. Its `foreground.argv` is `claude --model
  sonnet …`: the login shell found `claude`, and `exec` kept one process. Its `where` is `<home folder> / 1`:
  Herdr made a space for it, and the owner saw it as its own space.
- **A linked remote child, same way** (`--outlive-parent` in place of `--no-parent`):
  `vps/t2b`. hc recorded `parent: t1y` across machines, `claude` is the foreground program,
  and the owner saw it in Herdr. So both remote kinds are visible with the labels.
  Herdr's own app launcher does the same on remote Unix machines: it loads the user's
  login/interactive shell for sh, bash, zsh, dash and ksh, and keeps an sh launcher for other shells
  (`~/.config/herdr-app/AGENTS.md`, the programs section).
- **Herdr spaces** (`AGENTS.md` § The model): "A terminal with those labels [`herdr.space=<id>`,
  `herdr.tab=<id>`] shows up there, even one you start yourself: `hc run --keep --label
  herdr.space=<id> --label herdr.tab=<id> -- claude`." "An id Herdr doesn't know becomes a new space
  or tab." Labels use ids local to that machine (no `<machine>/` prefix). "Other machines' terminals
  stay out … unless Herdr started them for a space on that machine." Ids seen live: `sp` + 32 hex and
  `tb` + 32 hex.
- **hc parent.** `hc run` sets `parent` once (`--parent`, `--no-parent`). No verb changes it later,
  and `hc label` changes labels only. A child survives its lead terminal's death
  (`die_with_parent: false`, proved live).
- **hc wait** waits for a whole launch turn, so it cannot say "the child came up". There is no
  verb for "first status or exit". So the launch check reads `hc get` until a condition holds, with
  a deadline.
- **Screens (2.1.322).** A single AskUserQuestion shows a header line `☐ <header>`, options `1..n`,
  `n+1. Type something.`, a rule line, then `n+2. Chat about this`. Several questions show a tab row
  `←  ☐ A  ☐ B  ✔ Submit  →`. A multi-select shows `[ ]` boxes. A Bash permission's status msg is
  `approve Bash: <full command>`, not cut at 200 characters (323 seen).

## Approach

### Phase 1 — the relay and the lead check (BUG 2, BUG 3, BUG 7)

**The contract re-read (done in the main session, 2026-11-12, Claude Code 2.1.322 bundle).**
- The message builder `X9(text)` is `tp(text.replace(/\s+/g, " ").trim(), wg)` with `wg = 800`.
- `tp(e, n)` returns `e` when `e.length <= n`. Otherwise it returns `e.slice(0, n - 1) + "…"`,
  stepping back one more unit so a surrogate pair is never split.
- So every message has single spaces and is at most 800 UTF-16 units, and a cut one ends with "…".
- The permission form is `approve ${tool}: ${action}`. A prefix `<description> · ` may come first:
  the bundle matches `(?:^| · )approve `.
- The OSC writer then applies `d5(msg, re)` with `re = 2048`. It cuts to 2048 UTF-8 bytes with
  **no mark**, at a character boundary. Only non-ASCII text can reach 2048 bytes within 800 units.
  A cut result is at least 2045 bytes.
- The "cut at 200 characters" in `docs/claude-code-contract.md` (the OSC 7501 row) is wrong. Fix
  the row with these facts.

**BUG 2: long permission prompts.**
- Replace `STATUS_MESSAGE_LIMIT` with `RELAY_MESSAGE_LIMIT = 800` in `words.ts`: Claude Code's own
  cap. Its comment carries the facts above. The judge quotes up to that length, so its quote is
  always complete. Add one length helper used by both `answer` and the judge.
- `answer` refuses, and points to the pane, when the msg:
  - ends with "…" (Claude Code cut it);
  - is 2045 UTF-8 bytes or more (the transport may have cut it silently);
  - is longer than `RELAY_MESSAGE_LIMIT` (it cannot happen, so refuse).
- Parse the action after an optional `<description> · ` prefix.
- **Bash only:** `answer` requires the msg's action to match the dialog on screen.
  - The dialog region runs from the last rule line above the option block down to the first
    option. Earlier transcript lines never count.
  - With all whitespace removed (the screen wraps long commands), the action must equal a run of
    whole lines in that region, starting at a line start and ending at a line end. A cut action is
    then only part of a line and fails.
  - No match: refuse, "answer it in its pane".
- **Other tools (Write, Edit, …)** get the cut rules above but no screen match. The dialog may show
  a relative path, and no capture of it exists, so a screen match could break item 2's proved Write
  relay. The old 200-character refusal goes: the cut rules now detect a cut exactly. The docs say
  the person approves a path there, never the file's content.
- **The judge (the security edge).**
  - `herdrExcerpt` quotes `--expect` up to `RELAY_MESSAGE_LIMIT`, so the person's ask shows the
    whole prompt `answer` will relay.
  - The judge keeps only the first ask on a Bash line (`ask ??=`, `src/hooks/bash-judge.ts:686`). So
    it **denies** a line with more than one `herdr answer`, or an `answer` beside any other verb that
    asks. Each answer then gets its own approval. Tests cover both.

**BUG 3: a single question.**
- `answer` reads only the dialog region (as above) and refuses there on the signs of several
  questions or a multi-select:
  - a tab row: a line with two or more `☐`, or `✔ Submit`, or `←` … `→` (a narrow pane may drop
    some of these);
  - checkbox options `[ ]`, `[x]` or `[✔]` on an option line;
  - the existing `n/m questions` form.
- A lone `☐ <header>` line no longer refuses. Drop the bare `☐` and the loose `←…→/❮…❯` patterns,
  because `❯` is the cursor mark.
- `dialogOptions`:
  - Tests for a rule line (box-drawing characters only, any indent) before the continuation check
    at `command.ts:661`. Today an indented rule may be glued onto the "Type something." label.
  - Crosses a rule only when the next numbered line continues at n+1.
  - Copies the exact indentation from #273's capture into the test fixture. The live refusal came
    from the pattern check at `:705-710`, before `dialogOptions` ran, so the rule-line handling is
    proved by that fixture, not assumed.
- For a question:
  - `answer` finds "Type something" and "Chat about this" by label prefix and refuses `--option` on
    them;
  - it relays any of options 1..n above them;
  - the "always / don't ask again / for this session" label refusal (`:722`) applies to permissions
    only, so an option such as "Always use tabs" can be relayed.
- Fix the old fixture `"← Question 1 →\n1. A\n2. B"` (`command-scenarios.test.ts:414`): add `❯`, so
  it refuses for the tab row, not for a missing cursor.

**BUG 7: adopt and report disagree.**
- Add `isLiveClaude(t)` in `command.ts`: `state === "live"` and `status?.app === CLAUDE_CODE_APP`.
  It is the one home for "the lead is a live Claude".
- `send()` (`command.ts:377`) requires `isLiveClaude` too, so `report`, the `send` verb and any
  later caller never type into a bare shell. Its "done" path types with no `--if`, which makes
  this check matter. The test fixture is the real `hc get` of a bare-shell lead (`agent: zsh`,
  `status: null`).
- `report` sends when `isLiveClaude` holds and the state is `idle`, `working` or `done`; otherwise
  it saves the file.
- `adopt` skips the child only when the old lead `isLiveClaude`, in any state. So a lead blocked on
  a prompt is not taken over, and a lead terminal that is a bare shell counts as gone.
- `adopt` also lists the report files saved for each child it adopts (the child's brief folder,
  from `reportPath`'s folder). Reports saved while the lead was gone then reach the new lead.
- `report` keeps exit 0 on the file fallback. The report is kept and the line says so. A non-zero
  exit would make the child retry or stall, and it can do nothing better.

### Phase 2 — start (BUG 1, BUG 4, BUG 5, BUG 6), after Phase 1 (same file)

**BUG 1: a child that dies at launch.**
- After `hcRun`, `start` reads `hcGet` until the child reports a Claude status
  (`status.app === CLAUDE_CODE_APP`) or finishes. It stops at a deadline: one named constant,
  `LAUNCH_CHECK_MS = 20_000`, with the interval as another constant. `HerdrContext` gains `now()`
  and `sleep()`, with the real clock by default and a fast fake in tests. Polling is the only way:
  `hc wait` waits for the whole first turn.
- **Finished:**
  - print the last non-empty lines of its screen (`hcRead`), for example Claude Code's "Workspace
    trust not yet accepted …";
  - remove the finished terminal (`hcRm`), so a retry with the same `--name` is not refused at
    `:557`;
  - say whether the worktree folder exists;
  - exit 1, with no "linked child" line and no task binding.
- **Deadline with no status** (for example, a folder with no git repo that sits on the trust
  dialog): print the same screen lines, warn "has not reported yet; answer it in its pane: hc
  attach <t>", and exit 0.
- No trust pre-check. Claude Code keeps trust in its own private `~/.claude.json`, and reading that
  would tie the kit to an unpublished format. The launch check shows Claude's own message, which
  names the fix.

**BUG 4 and BUG 6: show sessions in Herdr's window.**
- In `labels.ts`: `HERDR_SPACE = "herdr.space"`, `HERDR_TAB = "herdr.tab"`, and
  `newHerdrSpace()` → `{ space: "sp" + 32 hex, tab: "tb" + 32 hex }`, from `crypto.randomUUID()`
  without dashes.
- `start --independent` (local or remote) and every remote start (`--on`, linked or independent)
  add `--keep` and the two labels with fresh ids. On a remote machine the ids are that machine's
  local ids, so no prefix.
- A local linked child stays as it is: it nests under its lead in the Agents panel (proved live).

**BUG 5: remote launch through the login shell.**
- One helper builds the argv that runs a program through the remote user's login shell, with the
  arguments passed as positional parameters. No user text is ever quoted into the script:
  `sh -c '<script>' kit <program> <args…>`. The script runs
  `exec "$SHELL" -lic 'exec "$0" "$@"' "$@"` when `$SHELL` is sh, bash, zsh, dash or ksh, and
  `exec sh -lc 'exec "$0" "$@"' "$@"` for any other shell. That matches Herdr's own launcher.
- The script is one named constant. Every level uses `exec`, so the terminal keeps one process:
  `foreground.argv` is Claude's own (`show()` reads `--model` there), and a dead launch ends the
  terminal as finished. Both `hc exec --on m -- sh -c …` and `hc run --on m … -- sh -c …` put `--`
  first.
- It is used for exactly two programs: the kit's `--version` check (through `hc exec --on`) and
  every `claude` launch, local and remote (through `hc run [--on …] -- <argv>`). The local launch
  needs it too (ruling, 2026-11-12): the Herdr core's PATH lacks the person's nvm `node`, so a
  local child's other-plugin hooks failed live with `Executable not found in $PATH: "node"`.
- `command-scenarios.test.ts:121` asserts that no remote call contains `sh`. Rewrite it on purpose:
  `sh` is allowed only on the two wrapped calls, with the script argument equal to the constant. `git`, `test`, `mkdir` and `chmod` stay on
  the plain path: they are system programs.
- Before the version check, a `claude --version` check through the same helper. Exit 127 (or no
  version printed) gives a clear refusal, `<program> is not installed on <machine> (not found by its
  login shell)`, with the fix: the installer line for the kit, Claude Code's install for `claude`.
- Parse the version as the last `\d+\.\d+\.\d+` in stdout, because an interactive shell's rc files
  may print other lines first.

## Patterns to follow

- Every hc call goes through `src/herdr/hc.ts` (`invoke`, `hcGet`, `hcRead`, `hcRun`), and tests use
  the fake `HcRunner`. No raw `Bun.spawn` for hc outside `followEvents`.
- Output goes through `ctx.out.line(kind, text, { fix })` (`.claude/rules/command-output.md`): a
  failure carries its fix.
- Constants have one home: label keys in `labels.ts`, limits in `words.ts`, launch timing in
  `command.ts` beside `WAIT_TIMEOUT_MS`.
- Tests build screens from the live captures in #273's notes, written by hand
  (`.claude/rules/testing.md`).

## Edge cases

- **The judge shows less than `answer` relays** (the security edge): one constant drives both; a
  test proves a 900-character `--expect` is quoted in full.
- **A cut status msg** (an older or newer Claude Code that cuts): an ending "…" refuses, and so does
  an action not found on screen.
- **A screen that wraps a long command**: compare with whitespace removed.
- **The same action twice on screen, or a prompt that changes mid-answer**: the existing turn,
  msg, option and cursor re-check just before `hc keys` stays. The window was judged acceptable in
  #273's item 10.
- **A numbered list above a rule line, then the options** (for example, a plan): reading across the
  rule gives numbers that do not run 1..n, so `dialogOptions` returns null and `answer` refuses. That
  is the safe outcome; a test covers it.
- **"Type something" or "Chat about this" chosen with `--option`**: refused.
- **A plan dialog**: still refused (unchanged).
- **The old lead terminal is a bare shell**: adopted (BUG 7). **The old lead is a live Claude blocked
  on a prompt**: not adopted. **The old lead terminal is finished or removed**: adopted (unchanged).
- **A new Claude starts in the old lead's terminal**: it is the lead by identity (`<core>/<address>`)
  and gets the children's reports with no adopt. That is by design; docs say so.
- **Adopt leaves hc's `parent` on the dead terminal**: hc cannot change it. Documented as a known
  limit; the live proof notes where Herdr's panel shows the adopted child.
- **A child exits at launch with `--task`**: no binding is written; the exit is 1.
- **A slow first status (a big repo, a slow machine)**: the deadline gives a warning, never a false
  failure.
- **A remote `$SHELL` unset or exotic (fish, nu)**: the sh login fallback. **A remote rc file prints
  to stdout**: the version parse takes the last semver. **`bash -i` without a tty prints job-control
  noise to stderr**: stderr is ignored on success.
- **An argument with quotes, spaces or `$`** (the brief path, the first message): passed as
  positional parameters, never inside the script text; a test proves `$(…)` and `'` come through
  unchanged.
- **Space ids collide**: random 128-bit ids, so no.
- **`--keep` after a core crash**: Herdr gives the terminal a shell in place and never re-runs
  `claude`. That matches Herdr's own panes.
- **Windows**: herdr verbs do not run on native Windows (hc is Unix-only), so there is no new path.

## What could break

- `STATUS_MESSAGE_LIMIT` has three users (command.ts, bash-judge.ts, words.ts); all move to the new
  name in Phase 1.
- `dialogOptions` is exported. Check its users and tests with a search before changing it.
- `report`'s and `adopt`'s changed checks: the scenario tests for report-to-blocked-lead and
  adopt-with-live-lead must still pass, and new ones are added.
- `start`'s output for a remote or independent session gains no new success line. A launch failure
  changes the exit to 1, so scenario tests that faked an instantly-finished child need a status.
- The router bundle does not import `src/herdr/`. After the build, `git diff --stat plugin/dist` must
  show no `router.js` line.

## A simpler approach?

- For BUG 5, absolute paths alone (`~/.local/bin/claude`) are simpler. But `claude` would then run
  with the bare PATH, so its hooks and MCP servers that need `bun`, `node` or `bunx` would break. The
  login-shell launch is what Herdr itself does.
- For BUG 1, skipping the check and documenting it leaves a false "started" line. That bug cost a
  proof round, so no.
- For BUG 7, dropping `adopt`'s liveness check (adopt any child whose lead is not me) would steal a
  live lead's children. No.

## Rollback

A new patch version with the 4.3.0 behaviour (`.claude/rules/bundles-and-releases.md` § Releasing).
No data, schema or user-file changes, so a revert of the merge commit and a release are enough.
