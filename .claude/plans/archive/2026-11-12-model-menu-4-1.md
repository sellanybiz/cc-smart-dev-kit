# 4.1.0: the model menu tells the truth, the status line names who really answers

**Summary.** While the gateway is on, the kit writes Claude Code's own `modelPicker` menu: one row per
Claude family, chosen by alias (never a model id), each row saying who really answers. The stale
"Fable 5.1" row goes, and so does the 4.0.0 Fable pin. The status line names the model that really
answered (a slot's backend or a fallback included), for the main session and for each subagent row.
A new task never joins a closed plan. The edge-case hunter runs on Opus, and the recommended option
is always the best one.

## Context

### Why `/model` shows Fable 5.1 (Claude Code 2.1.322's own code, traced and checked by hand)
- Behind `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>` the provider stays `firstParty`. ("gateway" in
  Claude Code means Anthropic's own Cloud gateway, never a base URL.) So the aliases resolve from the
  catalog baked into the installed Claude Code: `fable` → `claude-fable-5-2` already, pin or no pin.
  The router's history agrees for the others (opus-5-5, sonnet-5-5, haiku-5-5). These move forward
  with every Claude Code update: requests are already automatic.
- The "Fable 5.1" row is **server data**: Anthropic's bootstrap answer (`additional_model_options`),
  fetched straight from api.anthropic.com, cached in `~/.claude.json` `additionalModelOptionsCache`
  as `claude-fable-5-1[1m]`. It hides the compiled `fable` row. Picking it really uses 5.1.
- Without the pin, Fable stays usable: `QRe()` is true today (no catalog active, `firstParty`), so
  `/model fable` and an Agent `model: "fable"` resolve to 5.2. Watch point: if Anthropic turns its
  published catalog on, `QRe()` would need the pin, and Fable rows would hide (contract row).
- **Rejected after research:**
  - `_CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL=1` (undocumented; makes Claude Code treat the router as
    Anthropic's API). It puts a line that changes on every request at the very start of the system
    prompt (`cc_prev_req`, `cc_prev_msg`…), so backends lose their prompt cache, and the router may
    not edit prompt text. It moves auto-mode checks to Anthropic's servers (the judge chain is skipped
    for Claude requests), moves side queries to Haiku, and makes menu descriptions impossible. The
    owner chose it first, then chose the menu below with these facts (2026-11-12).
  - `ANTHROPIC_DEFAULT_<F>_MODEL_NAME/_DESCRIPTION`: read only together with the `_MODEL` pin.
  - Gateway model discovery (needs a token, key or `apiKeyHelper`; it only adds rows); the router
    rewriting ids (gateway rule); a fetch by the kit.
- **The way:** the `modelPicker` setting (schema confirmed in the binary): rows
  `{model: "<alias or id>", label?, description?, behavesAs?}`, and `replaceBuiltInOptions: true`
  shows only Default plus these rows (bootstrap and gateway rows hidden). `model` takes an alias.
  Not yet proved: how a row renders when `label` or `description` is left out (does Claude Code fill
  the version, as the built-in rows do?).

### The task bug (root cause)
`src/tasks/ops.ts:167`: `ownPlan` is the plan of the caller's newest own task with a plan, open or
closed. `task_create` with no `plan` and no parent (`ops.ts:334`) and a phase with no `plan`
(`ops.ts:260`) take it, so a new task joined the closed 4.0 plan (status line 17/18).

### Who really answers
- Every request carries `x-claude-code-session-id`; a subagent's adds `x-claude-code-agent-id`, its
  `agentId` (binary: `oe?.agentId&&{"x-claude-code-agent-id":…}`), and `x-claude-code-parent-agent-id`.
- The router's `history.db` `requests` table has `session, model, slot, profile, target, next_target`
  (`src/gateway/history.ts:143-164`, index `requests_session_at`), no agent column. The router reads
  only the session header (`router.ts:356-417`).
- The main status line shows stdin `model.display_name` and a limit banner `⚠ X at its limit → Y`
  from `gateway-state.json` (`statusline.ts:148-184`); it never reads the history. The subagent row
  shows `slot → Claude Code's resolved model → effort` (`subagent-statusline.ts:148-185`) from the
  task's `model`; its task `id` is the agent id (to prove live).

## Decisions (owner, 2026-11-11 and 2026-11-12)
- Models are fully automatic: never a model id written by the kit.
- **The kit's menu, no switch:** while the gateway is on, the kit owns `modelPicker` with alias rows
  and "answered by" descriptions. *Trade-off, written down:* the menu lists only the kit's rows plus
  Default; Anthropic's own extra rows are hidden while the gateway is on. A model Anthropic ships
  reaches the aliases with the Claude Code update that knows it (normally the same day), not from a
  live list.
- The status line and the subagent rows show who really answered, fallbacks included; the menu
  names each slot's first choice only.
- **Go fully new on the pin:** the pin and its setup step are deleted. One retirement remains (play
  safe for machines on 4.0.0): the pin is removed while it still holds the kit's value. It goes in
  the heavy cleanup once no machine runs 4.0.0.
- The edge-case hunter's recommended model is `opus`. The `(Recommended)` option is always the best
  complete one.
- One release, 4.1.0 (minor). The router restarts once (B).

### C. A new task never joins a closed plan

- **For writes,** the default plan is the caller's latest own plan (today's rule, `ops.ts:167`)

  says how: reopen the plan with `task_update`, or create a loose task. No open plan: a task with no
  parent is loose; a phase with no `plan` is refused as today.

## Edge cases
- **The person has their own `modelPicker`** (or the old pin): foreign, left alone, a `·` line.
- **A slot changes while sessions run:** settings changes reach running sessions within about a
  second; the menu follows. A fallback mid-session shows on the status line, not the menu.
- **Profiles and project gateways:** a profile launch gets its rows and `--no-gateway` plain-Claude
  rows (A); a project gateway cannot have its own menu (Claude Code reads `modelPicker` only from
  user, `--settings` and managed settings), so `gateway project` says so.
- **A concrete model saved by an old picker choice** (`model: claude-fable-5-1[1m]`): the doctor line.
- **Anthropic turns its published catalog on:** Fable needs the pin again (`QRe()`); the contract row
  names it, and the upgrade skill re-proves the menu each Claude Code version.
- **A brand-new Claude family** (not a new version): needs a `CLAUDE_FAMILIES` entry, as routing does.
- **History:** an old router writing while a new status line reads (no column) → null; two writers
  → SQLite's busy timeout, as today; a session id the router rejected → no row, no arrow.
- **Status line:** gateway off; first tick before any answer; plan mode with `opusplan`; a fallback
  to another Claude model (Opus → Sonnet) shows the arrow too.
- **Tasks:** a plan finished and a new one started in the same session; a phase whose plan row is gone.

## Next plan (owner, 2026-11-11), not built here
"A more important rule is needed for Claude: code simplicity, code structure, file structure,
naming. Keep code structured and organized, files organized; create helper functions, services etc.
and call them where needed, just like a senior company or developers manage it. Do a deep research
first."
- **The owner's meaning, the rule's first line:** "simplicity means keep things clean and organized;
  it does not mean bad and dumb code." Simple ≠ simplistic: complete, robust, readable, organized.
- Gap check (done): reuse, placement, file size and sibling naming live in `extract-or-duplicate`
  (the natural detailed home); core.md has the principle. Missing: when to split unique code by
  responsibility, not only by repetition; helper vs service vs module criteria; a conflict between
  "a long function used once stays" (`extract-or-duplicate:31`) and "split past about 100 lines"
  (`:72`); meaningful names for functions, variables, types and booleans; "cleaner" and "structural
  change" undefined; the builder agent has no simplicity line and does not preload the skill;
  review's evidence bar fits bugs better than design findings.
- Outside research (done, cited; to the archive with that plan): code must be easy for a reader, and
  nothing is built for a need that does not exist yet. A helper, service or file earns its place
  now: a real second caller, a simple interface over real work (Ousterhout's deep modules), or the
  project's own pattern. Candidate rules: build only what the task needs; extract for a second
  caller or to name a long block in code you touch; prefer deep units over pass-through ones; inline
  shared code back when it needs a flag per caller (Metz, GitLab); keep what changes together in one
  place; do not split what must be read together; a service changes state across several things
  (GitLab); each layer calls only the layers the project allows; project conventions first (PEP 8,
  Google, Angular); validate at the edges only; unasked cleanup stays out of the diff; comments say
  why; unused code goes. Naming: purpose for a new reader, length by scope, no repeated context, no
  `utils`/`helpers`/`misc` names, no made-up abbreviations, names by use. Files: follow the layout;
  new code beside its feature; one concept per file; split by concept, not by line count. Leave
  out: tiny functions as a goal, DRY at any cost, layers "for flexibility", hard line limits
  (Google's 40 lines is "a prompt to think").
