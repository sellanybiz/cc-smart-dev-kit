# PF2 — PF1's review findings

**Goal.** PF1 (merged, `9f7e2cf`) made the portal's actions run the CLI's own command in a child and read the machine's crew. Its focused review (Opus, xhigh) found one Medium and several Low findings. Fix them before 1.1.0's pull request.

## How to read
Open only the functions named below, by line range. Read `.claude/rules/hooks.md` § A crew session's own limits and `.claude/rules/portal.md` first. Give any wider reading to a scout subagent in the background, and keep only its conclusion.

## The findings, and the fix for each
1. **Medium — `crew answer --as-person` skips the bypass-mode refusal for any caller that is not a crew session.** `src/crew/command.ts:547,554` gives the flag to every CLI caller; `src/crew/caller.ts:117-120` sets `session = null` without looking, so the bypass check (`caller.ts:130-141`) never runs. A lead in bypass mode can answer a crew session with one flag (README names it). Fix: the flag means "no Claude session runs this": always run `callingSession`, and when `--as-person` is given and a session is found, refuse with one line (the flag is the portal's). **Verify first** that the portal's own child is never a descendant of a Claude session: the portal is started by a SessionStart hook's detached starter (`src/hooks/detached.ts`, `src/portal/lifecycle.ts`), so prove whether its process ancestry reaches the `claude` process, and design the check on that fact (if it can, the portal's child needs a way the person's session cannot copy — say what you chose and why). Test: `--as-person` from a bypass-mode session is refused; from the portal's child it works.
2. **Low — a crew session can unset its own `CC_SMART_DEV_KIT_CREW` on the command line** (`env -u CC_SMART_DEV_KIT_CREW cc-smart-dev-kit crew answer …`) and pass `caller.ts:85`'s check; no hook denies a crew session's `crew answer|stop|rm|resume|watch|lead tell` (`src/hooks/bash-judge.ts:516-530` covers `crew start` only). Fix: the Bash judge denies those in a crew session the way it denies `crew start` (the hook's env is the session's own, which a command line cannot unset), with the `crew report` step.
3. **Low — `CrewContext.asPerson` is dead code** (`src/crew/context.ts:38-43`, its comment no longer true; `src/crew/end.ts:77-78` never runs). Delete the field and those lines.
4. **Low — `crew lead tell`'s partial failure** (`src/crew/lead-tell.ts`, `recordLeadNotes`) stops at the first failure and never names the receivers after it. Name every receiver not recorded (or try the rest and name each failure). Test with three receivers failing in the middle.
5. **Low — `docs/design.md`'s D52 paragraph** says all four child actions run in the record's repository; `worktrees.clean` has no record and runs in the portal's own folder (`cleanWorktrees`, `src/portal/actions.ts`). Say so.
6. **Low — a `crew rm` cut at `CLI_CHILD_TIMEOUT_MS`** (`src/portal/cli-child.ts:28`) may have done part of its work; the timeout line should say so and point at `crew status` or running it again.
7. **Low — the live stream's byte limit:** `hub.test.ts`'s `expect(STREAM_QUEUE_MAX_BYTES).toBeGreaterThan(BUFFER_MAX)` compares bytes with an event count and cannot fail: replace it with "a full replay of realistic size fits under the limit"; and add a server-level test (through `Bun.serve`, a client that opens `/events` and does not read while events are published) that proves a stalled stream is closed — if it is not, fix the limit so it is.
8. **Low — `listAllLeads` copies `listAllCrew`'s walk** (`src/crew/store.ts` around 647-657): one `listAllRecords` that both call.
9. **Low — the Work page's note** about the portal's folder (`src/portal/api/work.ts`) shows in warn colour on every normal start (`portal/src/views/work.tsx`): muted for that note, warn kept for a store that cannot be read.
10. **Outside PF1, but the same rule:** `/api/worktrees` (`worktreesAnswer`, `src/portal/api/work.ts` around 772) calls `scanWorktrees` synchronously in a read path — move it off the server's event loop the way PF1 did the actions (the CLI's own `worktrees --json` in a child, shared and cached briefly, like `src/portal/flow-read.ts`).
