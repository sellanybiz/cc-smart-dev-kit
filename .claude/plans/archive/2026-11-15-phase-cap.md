# Plan: at most 10 phases per plan, each phase holds its tasks (4.8.0)

**Summary.** Plans have grown to 77 phases with filler tasks, and every phase gets its own review.
The cause is the plan skill's sizing rule, not a code bug, and nothing in the store stops it.
Fix: a phase becomes one area of code with real tasks; a plan holds at most `plans.maxPhases`
phases (default 10, set per project or per person); the store enforces it; old plans freeze.

## Context

Read-only look at the server's store (`~/.claude/cc-smart-dev-kit/tasks/work.db`):

| Plan | Phases | Tasks |
|---|---|---|
| #292 own stack, server track | 77 | 160, nearly all exactly 2 per phase |
| #264 React practices | 32 | 3; 30 phases have none |
| #2, #116, #144, #89 | 30, 28, 27, 23 | 55, 17, 29, 8 |

Root causes, checked in the code:
1. `plugin/skills/plan-task/SKILL.md:137`: "A phase is about 30 to 90 minutes of work. A bigger
   one splits before it starts." A big plan becomes dozens of phases; the real steps turn into
   phases and their tasks become filler ("do it" + "check it").
2. No cap anywhere: not in the skills, not in `src/tasks/` (`layPhase`, `src/tasks/work/store.ts:523`).
   Plans also grow mid-build (#264 gained P0/P1/P2/FR1, and holds "stage 1" and "stage 2").
3. `plugin/skills/build/SKILL.md` §3 runs one review per phase: 77 phases, 77 reviews.
4. A phase may start with no tasks (#264).

Decisions (the owner, 2026-11-15): a hard cap in code; default 10, changeable per project and
per person; plans already over the cap freeze (no new phases) and are named in warnings, nothing
rewritten.

## The model after this change

- **Plan** = one result you can ship. At most `plans.maxPhases` phases. Bigger work is a
  sequence of plans (the queued-plan pattern the kit already uses).
- **Phase** = one area of the code with its own file set: one builder, one review. It holds its
  real steps as tasks, usually 3 to 10, each with its check. Sized by files, not by minutes.
- **Task** = one step with its done-check. The builder closes them as it goes; the existing
  `builder-finish` guard already holds a hand-back while a blocking task is open.
- **Waves:** every phase with no open blocker starts in one message, each in its own worktree.
  With the cap and the default 10 subagents, a whole plan of independent phases can start at once.
- **No new phases mid-build.** New in-scope work becomes a task in the phase that owns its files;
  anything else is a follow-up project task or the next plan.
- **Reviews:** one per phase (at most the cap), then the final whole-branch review.
- **One active plan per session.** A session may hold queued plans, but builds one at a time:
  the store refuses a phase in a second plan while the caller's active plan (an own open plan
  with an open phase) is unfinished. With no plan named, new work goes to the active plan, never
  to the newest one (today's `writePlan` in `src/tasks/ops.ts` picks the newest: a bug).
- **Asks during a build** (the owner, 2026-11-15): in scope → a task under the phase that owns
  its files; for later → one task per ask in the queued next plan (made if needed), waiting
  there for a phase; a lasting duty → a project task file. When the next plan is designed, its
  waiting tasks move under its phases; a plan cannot close while one is open.
- **One plan = one pull request** (the owner, 2026-11-15). Phase branches stay local, merge into
  the plan branch and are never pushed or given a pull request. After each merged phase the plan
  branch is pushed (when `autoPush` is on; otherwise the build asks the person once). The one
  pull request opens after the final review passes, as `openPr` allows.

## Approach

### The setting: `plans.maxPhases` (a workflow number setting)

Reuse the workflow settings, which already do project → person → default, with `workflow
show`, `set [--project]`, `unset` and `propose` (`src/workflow/resolve.ts`, `commands.ts`,
`write.ts`). Add a `plans` group with `maxPhases` to `workflowSchema`
(`src/workflow/schema.ts`), a whole-number rule in `NUMBER_RULES` (min 1, max 50), default 10 in
`workflowDefaults`. No new reader, writer or file. In a project it lives in
`.claude/cc-smart-dev-kit.json` → `workflow.plans.maxPhases`; for the person, in
`~/.config/cc-smart-dev-kit/workflow.json`. The project wins.

### The guards, in the store (same for MCP tools and the CLI)

- **Cap on new phases:** `layPhase` takes the cap and, inside its write transaction, refuses a new
  phase id when the plan already holds `cap` phases that are not dropped. Re-laying an existing
  id still answers "it was there already". Refusal text: the plan, its count, the cap and where
  it comes from, and the two ways forward: add the work as tasks under the phase that owns its
  files, or start a next plan; or raise `plans.maxPhases`.
- **No empty phase starts:** moving a phase to `in_progress` (`updateTask`, and the CLI's
  `start`) refuses while it has no tasks, naming the call that adds one (`task_create` with
  `parent: "#n"`).
- `src/tasks/ops.ts` resolves the cap through the workflow resolver for the caller's checkout
  and passes it in. A broken personal file fails the call loudly and names the file, as
  `workflow show` does.
- **One active plan:** laying a phase in plan B, or starting any of its work, is refused while
  the caller holds another own open plan with an open phase. The refusal names plan A and says to
  queue the work as tasks in plan B instead.
- **The default plan** for a call that names none is the caller's active plan; with none active,
  the latest own open plan (as today).
- **A task may wait in a plan with no phase:** `task_create` with `parent` = the plan's `#n`
  makes a task directly under the plan; `task_update` with `parent` = a phase moves it there
  later. A plan's open blocking tasks already hold its close (`doneValid`).
- One helper counts a plan's live phases (in `src/tasks/work/queries.ts`); the guard, `task list`
  and doctor all use it.

### Warnings for old plans

- `task_list` with `scope: "plan"` shows `Phases n/cap` and marks a plan over the cap as frozen.
- `doctor`'s project checks (`src/cli/project-checks.ts`) print one `!` line per open plan over
  the cap, with its fix (finish it, or re-plan its remaining work as plans within the cap).

### The instructions

- `plan-task` §4 and §5: the model above replaces the 30-to-90-minute rule; the plan names its
  phases (at most the cap) and each phase's tasks; a plan that needs more becomes queued plans.
- `build` §1–§3: all ready phases start in one message; no new phases mid-build; one review per
  phase; the start guard and the cap refusal are named so a session knows the way forward.
- `core.md` § Drive the work: one line on the cap and phase shape (line budget 140).
- `plugin/agents/builder.md`: work the phase's tasks in order, closing each with its check.
- `memory-routing`, `subagent-decision`, and the tool descriptions in `src/tasks/schemas.ts` /
  `mcp.ts` say the same in their own place, never a copied sentence (`check:duplicates`).
- Docs: `docs/design/tasks.md` (§ The subagent ledger, § Layers), the workflow design page,
  `README.md` (workflow settings table), `CHANGELOG.md` 4.8.0.

## Edge cases

- **Two sessions laying phases at once:** the count and the insert run in one write transaction.
- **Re-laying an existing phase at the cap:** allowed; nothing new is made.
- **Dropped phases** do not count, so dropping a wrong phase frees its slot; done ones count.
- **Old plans over the cap** (#292, #264, ...): they keep running; any new phase is refused.
- **#264's 19 pending phases with no tasks** now need a task before they start. The refusal
  names the exact call. This is intended: it is the defect.
- **Cap lowered below a live plan's count:** same as an old plan: frozen, warned.
- **Broken personal workflow file:** phase creation fails, naming the file and field.
- **Bad value** (0, 1.5, text): the schema refuses it in the file, and `workflow set` refuses it.
- **No project config:** the person's value, else 10.
- **Queued plan created mid-build:** new work without a plan name still lands in the active plan.
- **Another session's plan:** "own" is the existing `owns` rule (created by or claimed by the
  caller); one session's active plan never blocks another session.
- **Taken plan (`task_take`):** after a take the taken plan may be the caller's second open plan
  with open phases; the take still works, and the refusal applies only to laying or starting
  work in the other one until one finishes.
- **Waiting tasks when a plan is designed:** they move under phases with `task_update parent`;
  one left under the plan holds its close, so it is either built or dropped with a reason.
- **Router bundle:** none of this is imported by `src/entries/router.ts`; check
  `git diff --stat plugin/dist` shows no `router.js` line.

## What could break

- Callers of `layPhase` and `updateTask` (ops, CLI command, import, repair, take): the cap and the
  empty-phase rule apply only to creating a new phase and to starting a phase. Import and repair
  never call those paths with a new phase; G checks every caller.
- The `tasks-mcp.js` bundle gains the workflow resolver; check its size and that it imports
  nothing from outside `plugin/`.

## A simpler approach?

Skill text alone was offered and declined: nothing would stop a plan from growing mid-build.
The setting reuses the workflow settings, so it adds no new file or command.

## Rollback

Revert the release with a new version. The setting is additive: an unknown `plans` key in an old
version's strict schema would fail, so a project that set it must unset it before downgrading
(the CHANGELOG says so).

## How we prove it

- Tests that fail without each change: the 11th phase refused, the 10th allowed, re-lay allowed,
  dropped not counted, project value over personal over default, empty phase start refused,
  doctor's line for an over-cap plan, `task list` count.
- `bun run check`, both validates, `build:check`, `router.js` unchanged.
- Live on this machine in a scratch project: 10 phases, the 11th refused; `workflow set
  plans.maxPhases 12 --project` lets it in; a phase with no tasks will not start.
- On the server after the update (the person runs it): `doctor` names #292, #264, #2, #116,
  #144, #89 (and #233 / #1 if over); a fresh plan in that project stays within 10.
