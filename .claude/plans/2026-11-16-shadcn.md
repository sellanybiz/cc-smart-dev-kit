# 4.10.0: shadcn support, and React best practices split from performance-budget

**Summary.**
- Every machine gets the official shadcn MCP server (pinned). The plugin ships the official
  shadcn skills and all five shadcncraft skills.
- Claude is made to reach for the project's design system before it hand-builds a control:
  through the builder, the brief, the review and the project's linter.
- `performance-budget` is split: a new `react-best-practices` skill takes the React
  playbook, React Compiler and design-system-first, and `performance-budget` keeps the
  performance and UX budgets.

## Context

An agent in another project found that Claude hand-built raw `<select>`, `<table>` and
`<textarea>` controls where the project's shadcn design system already had them. Its four
proposed kit changes were checked against the kit (2026-11-16). All four gaps are real:

1. **The builder never checks the design system.** `plugin/agents/builder.md:56-57` says
   only "Use existing code before adding a second implementation". It does not preload
   research-first.
2. **The brief has no slot for standard components.** `plan-task/SKILL.md:124-127` and
   `build/SKILL.md:64-66` give four brief parts, and none asks which standard component to
   use.
3. **Review axis 6 (`review/references/axes.md:21`) is vague for UI.** It never says a raw
   control is a finding.
4. **Nothing enforces it.** The project config has only `checks.fast`.

The reuse rule itself already exists (`core.md:22-25`, research-first, axis 6), so this plan
puts it where each decision is made rather than writing it a fifth time.

The person also asked for full shadcn support (the MCP server and skills, including
shadcncraft's), and said `performance-budget` is misnamed. It carries the vendored Vercel
"React Best Practices" playbook (4,287 lines) and React Compiler, and the builder loads it
on every React edit.

## Decisions (the person's, 2026-11-16)

- **shadcn MCP: on for every machine,** user scope, pinned in `MCP_VERSIONS`.
- **shadcncraft: all five ship with the plugin,** chosen against advice:
  - `generate-code` stops without a Pro key (`SHADCNCRAFT_LICENSE_KEY`) and needs the Figma
    MCP;
  - three of the others need the shadcncraft Figma kit;
  - `generate-code` fires on any "Figma to code" request.

  **Mitigation inside that choice:** each ships with `disable-model-invocation: true` (DMI).
  The person runs it as `/cc-smart-dev-kit:shadcncraft-<name>`, and Claude never starts it
  on its own. Claude Code's docs: "Description not in context, full skill loads when
  invoked" (code.claude.com/docs/en/skills). The trade-off: shadcncraft's own chain
  (import-app → import-block → import-component) becomes the person typing each step. The
  README and react-best-practices say so.
- **Context budget: one new always-on skill, small raise.**
  - `react-best-practices` is the only new skill Claude loads by itself.
  - The vendored `shadcn` and `migrate-radix-to-base` skills ship DMI. In a project with
    `components.json`, react-best-practices tells Claude to read the vendored
    `shadcn/SKILL.md` and its references as the design-system guide. The person can also run
    `/cc-smart-dev-kit:shadcn`.
  - The narrowed performance-budget description pays part of it. `ALWAYS_ON.max` then rises
    only by the measured remainder (about 40 tokens), with the reason in its comment.
- **Enforcement goes through the project's own linter, not a kit scanner:**
  - Biome `correctness.noRestrictedElements` (since 2.0) with an `overrides` entry that turns
    it off for the ui folder;
  - or ESLint `no-restricted-syntax` with JSX selectors, or `react/forbid-elements`.

  The kit's verify gate already runs the project's checks. The kit adds a `doctor` note when
  a shadcn project has no such rule.
- **Vendor, don't install per project.** Plugin skills reach every project with no step, and
  `npx skills add` would write outside the kit's managed writes. Both upstreams are MIT, and
  the notices travel with the files.
- **Neutrality: a new exception 4 in `.claude/rules/neutrality.md`.** The vendored folders,
  listed in the vendor table, keep upstream's names, URLs and license notices. Upstream's
  other-vendor agent configs (`agents/`) and its `evals/` are not vendored.

## Research (condensed; full sweep → `.claude/research/archive/2026-11-16-shadcn.md`)

**shadcn MCP server**
- npm `shadcn` 4.23.0 is the latest stable (2026-10-27). Node >= 20.18.1. Run as `shadcn mcp`.
- It has 7 tools: get_project_registries, list / search / view_items_in_registries,
  get_item_examples_from_registries, get_add_command_for_items, get_audit_checklist. It
  returns commands and never installs anything.
- It reads `components.json` and `package.json` from its process folder, the session's
  folder for a user-scope server. It has no per-call root, and `--cwd` only loads env files.
  So a builder's worktree is not seen: fine for browsing (same registries), but the add
  command runs in the worktree.
- With no `components.json` it still starts, and `@shadcn` works when named explicitly.
- Browsing needs the network. Private registries use env placeholders.

**Official skills** (MIT; shadcn-ui/ui at commit `e62c9435`, 2026-11-13)
- `skills/shadcn` is SKILL.md plus references, assets, scripts, evals and agents.
  - Upstream it is `user-invocable: false`.
  - Its `` !`npx shadcn@latest info --json` `` runs when the skill loads.
  - Its `allowed-tools` grant `shadcn@latest` CLI calls.
- `skills/migrate-radix-to-base`: needs a clean tree, a branch, and one commit per component.

**shadcncraft skills** (`@shadcncraft/skills` 0.2.0, 2026-09-21)
- The source repo is private, so vendor from the npm tarball, checked against the registry's
  `dist.integrity`. `LICENSE` sits only at `package/LICENSE`, so it is copied into each
  folder.
- The skill files are MIT. The product license forbids redistributing paid items, and allows
  AI tools.
- `generate-code`: Pro key, Figma MCP, an `@shadcncraft` registry in `components.json`.
- `import-variables`: works from local tokens.
- `import-app`, `import-block`, `import-component`: need the Figma kit, a Figma MCP and a
  running app.
- None has `allowed-tools`.

**Lint rules**
- Biome `noRestrictedElements` restricts tags only; it cannot target an attribute value.
- ESLint `no-restricted-syntax` selectors can (e.g. radio inputs).
- eslint-plugin-react 7.37.5 has `react/forbid-elements`. Its peer range does not declare
  ESLint 10.

## Edge cases (review axes)

1. **Correctness.**
   - The server reads the session's start folder, not a worktree, and its add commands are
     patched to the pinned `bunx` form. The skill text says to run them in the worktree.
   - When the person runs `/cc-smart-dev-kit:shadcn`, the vendored skill's `!` command runs.
     A live proof covers what Claude Code shows when it fails (no network, no
     `components.json`), and becomes a contract row.
2. **Performance.**
   - One more server process per session.
   - The first `bunx -y` fetch must fit the 30 s start limit. The pin keeps it fast, and
     doctor's 180 s `claude mcp get` warms the cache.
3. **Patterns.** The registration copies `sequential-thinking` exactly, including key order.
   Vendoring follows the playbook precedent.
4. **Boundaries.** Vendored folders are owned by the script, and excluded from formatting, so
   `bun run format` never rewrites them. The doctor note only reads.
5. **Shortcuts.** Every exclude and skip comes from the vendor table, never a hand list.
6. **Reuse.** Linter rules and upstream skills are reused. No kit scanner is written.
7. **Craft.** The kit's own text follows the plain wording rule. Vendored text is upstream's.
8. **Security.**
   - Vendored `allowed-tools` grant only `bunx shadcn@<pin> …`, reviewed in the final review.
   - Keys and registry tokens are named, never stored.
   - Tests use no network: hashes, not fetches.
9. **Neutrality.**
   - Exception 4 covers the vendored folders only.
   - `agents/` and `evals/` are not vendored.
   - The review reads the kit's own new text for names.
10. **Context budget.** One new always-on description. The raise equals the measured
    remainder, nothing more. If the DMI proof fails, the person decides again.
11. **Old data.** A project's `performance-budget.md` add-on is still read
    (react-best-practices falls back to it). Nothing else is stored.
12. **Conflicts.**
    - A project that ran `npx skills add shadcn/ui` keeps its own skill, and that copy wins
      (stated in react-best-practices).
    - A project `.mcp.json` `shadcn` gets the info line.

## What could break

- `SERVER_NAMES` consumers: every exact server list in the tests named above.
- `builder.md:59` and `axes.md:15` move to react-best-practices.
- Evals: two cases are added, and the baseline re-run is filed.
- `biome.json`, `check-docs` and `check-duplicates` gain table-driven excludes.
- The playbook path moves. Its only readers are the two skills' text.

## A simpler approach?

- Text changes only: does not meet "full support".
- Per-project `npx skills add`: no kit upkeep, but a step in every project, and writes
  outside the kit's managed writers.
- The vendor script plus hashes is the smaller long-term cost.

## Rollback

- Revert the pull request.
- To take the registration back, a follow-up version adds `shadcn` to
  `RETIRED_SERVER_NAMES` (`retired.ts` removes the kit's own registration).
- The skills leave with the plugin version.
